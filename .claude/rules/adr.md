# ADR Rules

このディレクトリで ADR を作成・編集する際は、以下のルールに従うこと。
 
## 目的
 
ADR は「なぜその設計を選んだか」を、却下した選択肢と理由込みで記録するもの。
「何がどうなっているか」はコードで分かるが、「なぜ他の選択肢ではないか」はコードに残らない。
数ヶ月後に同じ議論を再演させないために書く。
 
## 形式: MADR
 
- **Nygard形式（Context/Decision/Consequences）は使わない。MADRを使う。**
- 理由: Nygard には却下した選択肢の置き場が無い。furatora の ADR は代替案比較が主成分であり、「何を選んだか」より「何を却下したか」の記録に価値がある。
- 新規 ADR を書くときは、却下した選択肢とその根拠を必ずセクションとして含めること。

## ステータス管理
 
新規作成・更新時は以下のいずれかを設定する。
 
| ステータス | 意味 | 遷移条件 |
|---|---|---|
| `Proposed` | 提案済み。合意はあるが実装検証は未完了 | 新規作成時のデフォルト |
| `Accepted` | 実装・検証を通過した | 実装完了後、ユーザーの承認を得てから変更 |
| `Deprecated` | 非推奨。後継は無いが新規に従うべきではない | ユーザー指示があった場合のみ |
| `Superseded by ADR-000X` | 別のADRに置き換えられた | 新ADR作成と同時に旧ADR側を更新 |
 
**厳守事項: `Accepted` になった ADR の本文は書き換えない。**
 
- 決定が覆った場合は、既存ファイルを編集せず**新しい連番のADRを作成**する。
- 旧ADRは本文を変更せず、ステータス行のみ `Superseded by ADR-000X` に変更する。
- タスクの記録や例外の適用などを既存ADRに記載しないこと。
- この規則に反する編集（Accepted済みADRの本文修正）を求められたら、新規ADR作成を提案し、確認を取ること。

## ファイル命名・採番
 
- 形式: `NNNN-kebab-case-title.md`（0001から連番、4桁ゼロ埋め）
- 新規作成前に、既存ファイルを確認して次の連番を決定すること。
- **欠番・再利用は禁止。** 削除されたADRの番号を再利用しない。

## 書く内容 / 書かない内容の判定
 
新しい内容をADRに追加してよいか迷ったら、以下の表で判定する。
 
| 書く | 書かない → 移動先 |
|---|---|
| 覆すときに明示的な意思決定が必要な事項 | 時間とともに陳腐化する実装計画 → `docs/spec/tasks.md` |
| 却下した選択肢とその根拠 | 具体的な型定義・シグネチャ → `docs/spec/design.md` |
| 判断の前提となった実測値 | 未決事項・調査タスク → GitHub Issue |
 
ADR作成・編集タスクで「書かない」列に該当する内容を書こうとしていることに気づいたら、該当ファイル（`docs/spec/tasks.md` / `docs/spec/design.md`）またはGitHub Issueへの記載を提案し、ADR本文には含めない。
 
## 新規ADR作成時のチェックリスト
 
1. 既存ファイルをスキャンし、次の連番を確認する
2. MADR形式（却下案とその根拠を含む）で本文を作成する
3. ステータスは `Proposed` から開始する
4. 関連する既存ADRがある場合、参照リンクを追加する
5. このADRが既存ADRを置き換える場合、既存ADR側のステータスも同時に更新する
