## モデル

4層で持つ。**接続**が「どこからどこへ」、**接続とルートの紐付け**が「どの経路が
その接続で使えるか（識別名・基準ルートか）」、**ルート**が「どの経路で」、
**設備**が「何を使って」を表す。ペルソナは層にならない（設備から導出する）。

```
接続（無向1行・端点は 駅×方面、方面は必須）
  └─ 接続とルートの紐付け（0..N / label・isBaseline を持つ）
       └─ ルート（方面によって条件が変わらない接続どうしで共有されうる）
            └─ 設備（1..N / 直列に通る順）
                     → ペルソナ別の可否は表示層で導出（保存しない）
```

**ルートは接続に従属しない。** 決定4で方面を必須にした結果、方面差の無い駅は
駅対1組につき最大4行（方面2×2）の接続を持つ。これらが同じ物理経路を使うとき、
ルート行を4回複製するのではなく、**1本のルートを4つの接続から共有する**
（決定4）。`label` と `isBaseline` は「その接続でこのルートがどう機能するか」
という、接続とルートの組に属する事実なので、ルート自体ではなく紐付け側に置く
（決定10・11）。

### 接続 — 評価の単位

**無向のホーム方面対。** 端点は `(stationId, direction_type)`。**両方とも必須**
（`NULL` を許容しない）。

`stations` は路線×駅粒度なので `stationId` が路線を含意する（`docs/domain/
station-master-model.md`「駅の粒度」）。`direction_type` は `'inbound' | 'outbound'`
の2値で、`line_directions.id` を参照しない。**その駅でその路線をどちら向きに走るかという
走行上の事実だけを表し、乗換単位（物理ホーム）を一意に決めるものではない。**
分岐駅・同一駅を2回通る路線・直通運転を伴う分岐では、同じ `(stationId, direction_type)`
に複数のホームが対応しうる（決定4「方面キーの値域」の「影響」参照）。

端点を昇順に正規化して1行で持つ。方式は既存の `stationAdjacencies` と同じ
（`apps/admin/src/features/station-adjacency/domain/normalize.ts` の
`normalizeAdjacencyEndpoints()` を参考にする。当該関数は隣接専用の実装だが、
「端点を正規化して無向1行にする」という考え方は共有できる）。

```
端点A: (淡路町/丸ノ内線, outbound)   端点B: (小川町/都営新宿線, inbound)
端点A: (淡路町/丸ノ内線, outbound)   端点B: (小川町/都営新宿線, outbound)
端点A: (淡路町/丸ノ内線, inbound)    端点B: (小川町/都営新宿線, inbound)
端点A: (淡路町/丸ノ内線, inbound)    端点B: (小川町/都営新宿線, outbound)
  ← 池袋方面（outbound）側の2行は同一ルートを共有し、荻窪方面（inbound）側の
    2行も同一ルートを共有する。詳細は「方面の展開とルート共有」節
```

> **`stationId` が路線を含意するのは暫定である。**
> `stations` を物理駅粒度へ統合する [Issue #82](https://github.com/Natsugure/furatora/issues/82)
> が入ると、端点から路線が消える。正規化関数の比較キーには `direction_type` を必ず含め、
> 「`stationId` だけで端点が定まる」ことを前提にしたコードを書かないこと。

### 方面の展開とルート共有（REQ-3・REQ-5・REQ-23）

問い合わせは常に `(stationA, directionA, stationB, directionB)` の完全一致で行う。
一意制約（`unique(stationA, directionA, stationB, directionB)`）により該当行は高々1件
なので、**優先順位規則もタイブレークも要らない**。

方面によって評価が変わらない駅（大半の駅）は、方面の組み合わせ分（最大4行）の接続
それぞれが**同一のルート**と結び付く。値を4回複製するのではなく、1本のルートを
複数の接続から参照する（REQ-5・REQ-23。次節の「接続とルートの紐付け」を参照）。
淡路町↔小川町のように片側の方面だけ条件が変わる駅は、条件が変わる側の2行が一方のルートを、
残り2行がもう一方のルートを参照する形になる。

### 保持する事実

**接続に1つ**

| フィールド | 型 | 意味 |
|---|---|---|
| `notes` | 自由記述 | 接続全体に関わる備考 |
| `source` | 列挙 | 行の由来（`ekidata_group` / `manual` / `NULL`。現行を踏襲） |

**接続とルートの紐付けごと**（`connection_routes`。決定10・11で位置を移した）

| フィールド | 型 | 意味 |
|---|---|---|
| `label` | 文字列・接続内で一意 | 経路の識別名（「北改札経由」「地上経由」）。ルートが複数の接続から共有される場合、この列は紐付けごとに持つ（ルート自体は特定の接続に属さないため） |
| `isBaseline` | 真偽・接続あたり高々1本 | 一般利用者が案内される経路か（迂回度の分母） |

**ルートごと（ペルソナ非依存・接続に従属しない）**

| フィールド | 型 | 意味 |
|---|---|---|
| `minutes` | 数値（分） | そのルートの所要時分 |
| `isOutdoor` | 真偽 | 屋外を通るか |
| `requiresExitGate` | 真偽 | 改札外を経由するか |
| `requiresStaff` | 真偽 | 係員対応が必要か |
| `isOfficiallyGuided` | 真偽 | 事業者が公式に案内しているか |
| `notes` | 自由記述 | そのルートの備考 |

**設備（ルートごとに1..N、直列順）**

`same_floor` / `elevator` / `ramp` / `wheelchair_escalator` / `escalator` /
`stair_lift` / `stairs` の7値。

既存の `facility_types`（`elevator` / `escalator` / `ramp` / `sameFloor` /
`stairLift` / `stairs`）とほぼ同じ語彙を採用する。追加が必要なのは
`wheelchair_escalator`（車いす対応・係員操作のエスカレーター）のみで、淡路町の実データ
「途中車いす対応エスカレーターを使う必要があります」が要求している。
なお `ramp` と `stairLift` は `facility_types` に定義済みだが、`station_facilities`
の実データは0件（未実測の値）。

> **設備の並びは「直列」だけを表す。**
> 同じ段差に対する代替手段（階段と階段昇降機が並んでいる箇所）は、1本のルートに
> 2つ並べてはならない。**別のルート行**にする。この帰属規則が、
> 「階段昇降機のルートはベビーカーが通れない」という判定（REQ-13）を正しく機能させる。

### 導出する値（表示層の純粋関数。保存しない）

設備 → 必要な行為 → ルートの必要な行為 → バリアフリールート集合 → 表示、の順に導出する。
規則は REQ-13〜18 に表で置いた。実装は1つの関数に閉じる。

```ts
type Requirement =
  | 'as_is'             // そのまま通れる
  | 'call_staff'        // 係員を呼ぶ
  | 'fold_and_carry'    // 畳んで抱える
  | 'lift'              // 持ち上げる
  | 'assisted_by_staff' // 駅員複数名の介助
  | 'impossible';       // 通れない

// 経路上の直列な設備すべてを見て、そのペルソナにとって最も重いものを返す。
// 「重さ」の順序はペルソナごとに違い、この関数の中だけに存在する。
function requirementFor(persona: Persona, facilities: FacilityType[]): Requirement;

// バリアフリールート = 必要な行為が as_is または call_staff のルート（REQ-15）
const stepFree = routes.filter((r) =>
  ['as_is', 'call_staff'].includes(requirementFor(persona, r.facilities)));
```

変換は ADR-0003 の既存決定（「difficulty から表示色やラベルを決める変換はDTOの責務では
ない」）に合わせ、表示層に置く。現行の `apps/web/src/constants/difficulty.ts` /
`apps/admin/src/constants/difficulty.ts` と同じ位置づけになる。
**DTO はルートと設備をそのまま運び、ペルソナで絞り込まない**（絞り込みも解釈である）。

迂回度は「そのペルソナのバリアフリールートのうち最短の `minutes`」−「基準ルートの
`minutes`」で導出する（REQ-18）。基準ルートが高々1本に制約されているため、
分母は常に一意に決まる。

### 不変条件（DBで守るもの / アプリで守るもの）

| 不変条件 | 守り方 |
|---|---|
| 同じ端点対の行が2つない | `unique (stationA, directionA, stationB, directionB)`。方面が両端点とも `NOT NULL` のため `NULLS NOT DISTINCT` は不要（決定4） |
| 基準ルートは接続あたり1本 | `connection_routes` への部分ユニークインデックス `(connectionId) where is_baseline`。drizzle-orm 0.45.1 は `uniqueIndex().on().where()` で書ける |
| 同一接続内でルート名が重複しない | `connection_routes` への `unique (connectionId, label)`。ルートは特定の接続に属さないため、`transfer_routes` 側には置けない（決定11） |
| 設備の並びが壊れない | `unique (routeId, seq)` |
| 設備の並びと4フラグが既存ルートと完全一致しない | **アプリ層**（集合の一意性は制約で書けない）。Admin の保存時チェックを**接続をまたいで**行い（REQ-23）、一致する既存ルートがあれば新規作成せず紐付け（共有）を提案する |
| 基準ルートの付け替えが中途半端に終わらない | Repository + `withTransaction`（ADR-0005）。既存の降格と新規の昇格を1トランザクションで行う |

**行数の上限は制約で表現しない。** PostgreSQL の制約は行数を数えられない。
「無限にルートを足せる」ことへの実質的な歯止めは、`label` の一意制約（同じ名前で2本作れない）と
上記の重複検出であり、上限値そのものは置かない。

### 持たないもの

| 対象 | 理由 / 行き先 |
|---|---|
| おすすめ度・合理性・推奨乗換駅 | 出発地・目的地に依存し、接続単体の属性にできない（決定1） |
| ペルソナごとの可否・所要時分・フラグ | 設備から導出する（決定2・決定3） |
| 方面粒度で救えない方向依存（上り専用エスカレーター等） | 備考（決定9） |
| 設備の質（EVのサイズ、スロープの勾配） | 備考（決定9） |
| 時間帯制約（早朝深夜のEV停止、係員の不在）、工事中の仮設ルート | 備考（決定9 / Issue #120） |
| 改札外ルートの運賃上の扱い（追加運賃・IC の出場入場） | `requiresStaff` と備考（決定7） |
| 方面を表す `NULL`（全方面共通のワイルドカード） | 方面は両端点とも必須。全方面共通はルート共有で表現する（決定4） |
| 分岐駅の物理ホーム区別（中野坂上型） | `direction_type` は走行上の事実のみを表す。ホームの区別は [Issue #128](https://github.com/Natsugure/furatora/issues/128) の対象（決定4） |

## 決定記録

いずれも既存ADRの決定に反しない（ADR-0003 の DTO 責務分離方針を踏襲する形）ため、
新規ADRは作成しない。乗換難易度というドメインのモデル化そのものの決定であり、本文書に
決定記録として残す。

### 決定1 — 接続は事実のみを持ち、推奨・合理性を持たない

**決定**: 乗換難易度は出発地・目的地に依存しない事実のみを保持し、
「どの乗換駅を使うべきか」「この接続は推奨できるか」は保持しない。

**コンテキスト**: 現行の `discouraged`（「可能だが非合理的で推奨できない」）や
実データの備考「隣の大手町駅のほうが便利です」は、出発地・目的地が決まって初めて言える
経路上の選好を、接続の属性として断定している。有楽町線↔副都心線の池袋駅の例
（要町の接続パラメータ自体は良好でも、東池袋方面↔雑司が谷方面間の乗り換えに要町を
案内すると折返し乗車になるため案内できない）は、良し悪しが接続の外側（出発地・目的地・
進行方向）で決まることを示す。

**オプション**:
- (a) 事実のみ保持し、推奨・合理性は持たない（採用）
- (b) 事実に加え、接続単体の「おすすめ度」を人手で付与する列も持つ
  — 却下。要町の例のように、接続単体では正しい可否と、経路全体で見た案内可否が
  食い違う場合に、どちらが正なのか規則が要る。矛盾する二つの真実を同居させるだけになる。
- (c) 経路探索の設計を先にやり、そこから逆算して接続が持つべき属性を決める
  — 却下。手戻りは少ないが、未実装の機能の設計が本Issueより先行し、スコープが膨らむ。

**理論的根拠**: 「どの乗換駅を使うべきか」は接続そのものの属性ではなく、
出発地・目的地・進行方向を入力に取る別の計算（経路探索）の出力である。

**影響**: 推奨乗換駅の判定機能は本Issueでは実装されない。将来の経路探索機能で
本モデルの事実（ルートの設備・時分・4フラグ）を入力として解く。
複数ルートの並べ替えにも影響する（決定12）。

**レビュー**: 経路探索機能（Issue #119）の設計時に、本モデルの事実だけで十分かを再確認する。

### 決定2 — 値域は設備、ペルソナ別の可否は導出する

**決定**: 保存するのは「どの設備を通るか」であり、ペルソナごとの可否・必要な行為は
表示層の変換関数で導出する。

**コンテキスト**: エスカレーターと階段昇降機で、2ペルソナの可否が逆転する。
階段昇降機はベビーカーが使えず（固定用の台で、通れない）、車いすは係員操作で使える
（三田駅: 浅草線↔三田線）。一般的なエスカレーターは車いすが使えず、ベビーカーは
畳んで抱えれば使える（ただし双子連れ・多荷物では現実的でない — 開発者指摘）。

**オプション**:
- (a) 値域を設備にし、可否は導出する（採用）
- (b) 値域を「ペルソナごとの可否」（可能 / 係員対応で可能 / 不可能）にし、人手で入力する
  — 却下。同じ設備について2回判断が必要になり、「なぜそうなのか」という事実
  （階段昇降機だから、という理由）が備考にしか残らない。さらに検証中、
  「エスカレーター＝ベビーカー可」という解釈自体を訂正する必要が生じた。
  事実を保存していたため変換関数1箇所の修正で済んだが、可否を直接保存する設計であれば
  入力済みの全行を洗い直す必要があった。
- (c) 単一の順序尺度（1軸5段階）にする — 却下。エスカレーターと階段昇降機の可否逆転を
  単一の順序で表現できない（どちらを「重い」側に置いても片方が壊れる）。

**理論的根拠**: (a) は事実と解釈を分離するため、解釈の誤りが訂正コストの低い箇所
（変換関数）に閉じる。(b)(c) は事実と解釈を融合するため、解釈の誤りがデータ全体に波及する。

**影響**: 「最弱リンクを1つ選んで保存する」初版の方式も、この決定と矛盾していた
（最弱を選ぶには順序が必要だが、順序はペルソナごとにしか定まらない）。
改訂版は**設備を集合（直列の並び）で保存し、順序付けを `requirementFor` の中だけに置く**
ことでこの矛盾を解消した。REQ-14 の「重さ」の順序は関数の実装詳細である。

**レビュー**: 変換関数の実装時に、REQ-13〜15 の表を1対1でテストする。

### 決定3 — ペルソナで列を分けるのではなく、ルートを行として持つ

**決定**: 接続とペルソナの間に「ルート」を置き、1本のルート＝1つの物理経路として行で持つ。
ペルソナごとの列（`stroller_*` / `wheelchair_*`）は持たない。

**コンテキスト**: 初版はこの決定を「`stepFreeVia` / `routeMinutes` / 3フラグを
ペルソナごとに個別の値として持つ」としていた。根拠は三田駅（浅草線↔三田線）で
ベビーカーは階段、車いすは階段昇降機と**経路そのものがペルソナで分岐する**ことだった。
レビューで実在8シチュエーションに当てはめた結果、この根拠自体が
「足りていない次元はペルソナではなくルートである」ことの証拠だと判明した。
初版で表現できなかったのは次の3件。

| 実例 | 初版の限界 |
|---|---|
| 西日暮里（千代田線↔JR） | 車いすに ①階段昇降機＋駅員介助（屋内・短い） ②改札外EV（屋外・遠回り・介助不要）の2択があるが、1ペルソナ1組の値しか持てず片方が備考に落ちる |
| 高田馬場 vs 御茶ノ水 | 一般ルートに所要時分しか持てないため、「一般は屋内／自分だけ屋外」と「誰でも屋外」が同じ行になる |
| 霞ケ関・三田（ベビーカー） | バリアフリールートが存在しないことを表す値が無く、`stairs` と書くと REQ-13 の判定が崩れ、`NULL` と書くと未評価と区別できない |

**オプション**:
- (a) ルートを行として持つ（採用）
- (b) ペルソナごとに列を持つ（初版。撤回） — 却下。上表の3件を表現できない。
  さらに①同じ経路について同じ事実を2回書くため Admin にコピー機能が必要になり、
  ②同一の物理経路に対してペルソナ別に矛盾した値（一方は屋外、他方は屋内）を
  入力できてしまい、③指摘を埋めると列が23まで増え、ペルソナが3つ目に増えると
  6列単位で伸びる。
- (c) ペルソナ別の列を維持し、複数経路がある接続だけ備考で説明する — 却下。
  西日暮里型は「稀な例外」ではなく、階段昇降機やエスカレーターが絡む接続で構造的に起きる。
  また、選択肢を1つに潰す判断を入力者が利用者の代わりに下すことになり、決定8（可否を
  断定せず「何が必要か」を示して判断を委ねる）と正面から衝突する。

**理論的根拠**: 三田駅で「経路がペルソナで分岐する」ように見えたのは、
1つの接続に複数の経路が存在し、ペルソナによって通れる経路が違うからである。
ペルソナで列を割るのは、欠けている「ルート」の次元をペルソナで代用する回避策であり、
代用しきれない（同一ペルソナに2経路ある西日暮里で破れる）。

**影響**: テーブルが1つから3つになり、表示には2段の JOIN が要る。
一方で、ペルソナ間コピー機能（初版の Issue #124 検討事項）は不要になり、
1接続あたりの入力は「基準ルート1行＋必要ならバリアフリールート」に減る。
指摘A（ルートなし）・D（一般ルートの属性）・F（最弱リンクの矛盾）も構造的に解決する。

再改訂（決定4）で、ルートは接続に従属しなくなった（`connection_routes` という
中間テーブルで多対多に結ぶ）。「1本のルート＝1つの物理経路」という本決定の核は
変わらないが、方面差の無い駅では同一の物理経路が複数の接続から参照されるようになった。
これは REQ-23（同一経路の二重登録防止）が元々「事実が一致すれば同じルートとして扱う」
と定めていたことの、接続をまたいだ自然な一般化である（決定4参照）。

**レビュー**: 実データの入力が進んだ段階で、1接続あたりのルート数の分布を確認する
（大半が1〜2本であれば、この構造の維持コストは低いままである）。

### 決定4 — 粒度は方面×方面、方面キーは `direction_type`、全方面共通はルート共有で表す

**決定**: 評価の単位は駅×駅ではなく方面×方面とする。方面の値域は `line_directions.id`
ではなく `direction_type`（`'inbound' | 'outbound'`）とし、両端点とも必須（`NULL` を
許容しない）。方面によって評価が変わらない駅は、方面の組み合わせ分（最大4行）の
接続それぞれを作った上で、**同一のルートを複数の接続から共有する**ことで
「全方面共通」を表す。

**コンテキスト**: 淡路町↔小川町では丸ノ内線の方面によって条件が異なる
（池袋方面は途中階段、荻窪方面はエレベーターのみ）。都営浅草線・新宿線・日比谷線にも
方面別に条件が異なる駅が多数あるとの開発者指摘があった。番線（`platforms`。実データ
20駅40行、公開駅334件に対し登録率が低い）を必須にする案は、難易度を書く前に番線登録が
必須という制約が強すぎるため検討の初期段階で却下した。

初版（2026-09-21朝）は方面キーに `line_directions.id` を採用し、`NULL` を
「全方面共通」のワイルドカードとして許容していた。レビューで3つの欠陥が判明した。

1. `line_directions` は 602路線中14路線にしか存在せず、大半の路線で方面別評価を
   書けない
2. 同一 `(line, direction_type)` に対し `line_directions` に複数の同義行が存在する
   （丸ノ内線 inbound に「荻窪方面」相当が4行）。入力者が別行を選ぶと解決規則の
   優先順位が静かに外れ、**エラーにならず**全方面共通行へフォールバックし、例外が消える
3. `NULL` を識別子に混ぜたことで `NULLS NOT DISTINCT`・3段の優先順位＋タイブレーク・
   DB制約で防げない不整合（片側指定が両側分同時に存在）が必要になった

方面キーを `direction_type` に倒したうえで、「全方面共通」の表し方を4案検討した。

**オプション**:
- (a) `direction_type` + 全方面共通は `NULL` で表現 — 却下。上記3欠陥のうち2・3が
      そのまま残る（1は解消する）
- (b) `direction_type` を必須にし、全方面共通は4行に完全展開、値は重複コピーする
      （淡路町の設備列を2回ずつ、住吉の基準ルートを2回ずつ書く） — 却下。西日暮里型
      （同一接続に複数ルート）が絡むと重複が掛け算になる。片方だけ直すと静かに食い違う
- (c) `direction_type` を必須にし、接続は駅対のみで識別、方面はルートの適用条件
      （`route_id, station_id, direction` の行が無ければ全方面）として持つ — 却下。
      「行が無い＝全方面」という不在による表現が、REQ-4 の「行が0件＝未評価」と同型に
      なり、**意図的な「全方面」と未入力を区別できない**。`transfer_routes` に
      `direction_scope: 'all' | 'restricted'` 列を足せば区別できるが（案3′）、
      `isBaseline` の一意性が「接続あたり1本」から「条件の組ごとに1本」に緩み、
      DB制約で書けずアプリ層（ADR-0005）に落ちる
- (d) `direction_type` を必須にし、全方面共通は4行に展開したうえで、**同一の物理ルートを
      複数の接続から共有する**（採用）。淡路町・住吉ともに重複コピーが起きず、
      全方面共通が「4行が同一ルートを参照する」という積極的な事実として表現される

**理論的根拠**: (d) は REQ-23 が既に定めている「設備の並びと4フラグが完全一致する
ルートは同一ルートとして扱う」という原則を、接続をまたいで一般化しただけであり、
新しい仮定を追加していない。(c) が `NULL` の代わりに導入した「不在の兼用」を避けつつ、
(b) の重複コピーも避ける。`is_baseline` の一意性も「接続あたり1本」のまま
`connection_routes`（接続とルートの紐付け）への部分ユニークインデックスで DB に守らせられる。

**影響**: `transfer_routes` は `connectionId` を持たなくなり、`connection_routes` という
中間テーブルで接続と多対多に結ばれる。`label` と `isBaseline` はこの中間テーブル側に
移る（決定10・11改訂）。解決規則の優先順位・タイブレークは不要になった（REQ-3改訂）。

**中野坂上型（クラス1: 完全分離支線＋分岐）はこの決定では解決しない。**
`0007_fold_branch_lines.sql` が丸ノ内線支線を本線に畳んだため、中野坂上/丸ノ内線の
`direction_type=inbound` が本線ホームと支線ホームの両方を指す。`direction_type` を
どう値を取ろうと、同一 `stationId` が2つの物理ホームを指す限り区別できない
（初版が採用していた `line_directions.id` だけは、本線・支線が別の代表駅を持つ行として
登録されていたため区別できていた）。恒久的な解は `0007` で畳んだ支線を別 `line` に
戻すこと（[Issue #128](https://github.com/Natsugure/furatora/issues/128)。
Issue #83「運行系統のデータ投入と管理UI」とは別の話である。#83 は総武本線/総武快速線・
JR琵琶湖線/京都線/神戸線のような、正式路線名が実際の案内・運行形態と異なる問題
（案内路線と運行系統の分離）を扱い、本件は ekidata が物理的に分離した支線を本線に
畳んだことによる粒度の問題であり、性質が異なる。開発者確認済み・2026-09-25）。
実害は現状**中野坂上1駅**に閉じている（公開駅334件のうち、路線内で隣接次数3以上の
分岐駅は2駅、うち乗換接続を持つのは中野坂上のみ。実測 2026-09-21）。
本Issueでは解決せず、既知の制約として記録する（requirements.md「対象外」）。

**レビュー**: 番線（`platforms`）の登録が進んだ段階で、番線粒度への昇格が必要かを
再検討する。[#128](https://github.com/Natsugure/furatora/issues/128) 着手時、
中野坂上の `stationId` 分離後にこの決定が変更を要するか再確認する。
`connection_routes` への `label` 非正規化が #122 のスキーマ実装で
drizzle-orm により自然に表現できるか確認する。

### 決定5 — 向きは無向1行に正規化する

**決定**: 評価は無向として、端点を正規化した1行で保持する。現行の「有向2行に同じ値を
入れる」運用は廃止する。

**コンテキスト**: 決定4で方面を導入すると、有向2行の運用が成立しなくなる。
淡路町→小川町（池袋方面から本八幡方面へ）の逆方向は、「小川町の新宿方面ホーム →
淡路町の荻窪方面ホーム」であり、**同じホーム対ではない**。値をコピーできない。
一方、同じホーム対の往復（P→Q と Q→P）は通常同じ経路なので、無向1行にまとめられる。

**オプション**:
- (a) 無向、端点を昇順正規化した1行（採用）
- (b) 有向2行を維持する — 却下。方面を入れた場合コピーできる前提が崩れ、
      全行を独立に手入力することになり、決定4の目的と矛盾する。

**理論的根拠**: `stationAdjacencies`（隣接）が同じ問題を「無向1行・端点昇順正規化・
読み取り側が両方向を見る」で解決した前例がある。

**影響**: 読み取り側は端点の両順序（A,B）と（B,A）を見る必要がある。書き込み側は
INSERT前に正規化関数を通す必要がある。実データでの効果は、main の有向行が
池袋56行→28組、新橋42行→21組、飯田橋・北千住20行→10組に減ること。
上り専用エスカレーターのような、往復で経路が異なる稀なケースは備考に落ちる（決定9）。

**レビュー**: 往復で経路が異なるケースの実例が一定数見つかった場合、有向化を再検討する。

### 決定6 — 迂回度は持たず、基準ルートとの差から導出する

**決定**: 「迂回度」という軸を直接保存せず、基準ルートの `minutes` と、そのペルソナの
バリアフリールートのうち最短の `minutes` の差・比から導出する。

**コンテキスト**: Issue #30 が提案する4軸の一つ「迂回度合」を、時分軸と独立に
持つべきか検討した。「小/中/大」のような人手判定の順序尺度は、判定基準が
言語化されないまま入力者ごとにブレる恐れがある。

**オプション**:
- (a) 迂回度は持たず、2つの時分の差から導出する（採用）
- (b) 独立した順序尺度として人手入力する — 却下。基準が言語化できず
      （「12分ならどの段階か」に答えがない）、入力者間でブレる。
- (c) 迂回度を持たず、時分のみ持つ（差・比の導出もしない） — 却下。
      「一般ルートと比べてどれだけ迂回するか」は利用者にとって意味のある情報であり、
      導出さえすれば追加の保存コストなく提供できる。

**理論的根拠**: 2つの時分を持てば迂回度は数値として一意に決まり、主観的な判定基準を
作らずに済む。

**影響**: 分母が一意でなければ迂回度が定まらないため、基準ルートを接続あたり1本に
制約する（決定10。`connection_routes` への部分ユニークインデックスで守る）。
基準ルート自体がバリアフリールートである接続（明治神宮前）では迂回度0になる。
なお差には「距離の差」と「移動速度の差」が混ざるため、迂回度は必要な行為と併記する
（決定12）。

**レビュー**: 実装Issueで、後楽園↔春日（改札内3分／改札外経由で大回り）のような
実例を使って導出結果が妥当か確認する。

### 決定7 — 4軸目を屋外・改札外・係員・公式案内の4フラグに分解する

**決定**: Issue #30 の4軸目「屋外乗り換え・係員対応の必要性」を、独立した真偽値に分解し、
さらに「事業者が公式に案内しているか」を加えて4つとする。

**コンテキスト**: 実例を洗い出すと、独立に組み合わさるケースが実在する。

| 実例 | 屋外 | 改札外 | 係員 | 公式案内 |
|---|---|---|---|---|
| 御茶ノ水 | ○ | ○ | ✕ | ○ |
| 後楽園↔春日 | ✕（屋内） | ○ | ✕ | **✕** |
| 北千住・後楽園（丸ノ内↔南北）・日比谷 | ✕ | ○ | **○** | ✕ |
| 三田・霞ケ関 | ✕ | ✕（改札内） | ○ | ○ |

**オプション**:
- (a) 4つの独立フラグに分解する（採用）
- (b) Issue記載どおり1軸にまとめる — 却下。上表のとおり全パターンが実在し、
      1軸では後楽園↔春日（改札外だが屋内）と三田（改札内だが係員必須）を区別できない。
- (c) 屋外・改札外・係員の3つにとどめ、公式案内の有無は備考に書く — 却下。
      レビューで提示された8シチュエーションのうち3つ（後楽園↔春日・西日暮里・北千住）が
      「公式案内のない改札外ルート」であり、頻度が高い。かつ利用者にとっては
      「構内図に出ていない／駅員に聞いても案内されない」という判断材料になる。
      出発地に依存しない接続の事実なので決定1の排除対象でもない。

**理論的根拠**: 独立変数であることが実データで確認できた以上、まとめると情報が失われる。
北千住型（設備はエレベーターなのに係員が必要）は、`requiresStaff` を設備から導出できない
ことの直接の証拠である。

**影響**: `requiresStaff` には「設備の操作に係員が要る」と「改札の出入りの運賃処理に
係員が要る」の2つの意味が混ざる。後者は同一事業者の改札を出入りする後楽園
（丸ノ内線↔南北線）のようなケースで発生する。切り分けは `notes` に書き、
構造化は実データの蓄積後に判断する（要件の「対象外」）。

**レビュー**: 運賃処理由来の `requiresStaff` が一定数蓄積したら、専用フラグへの分離を検討する。

### 決定8 — 表示は「何が必要か」の6分類を導出する

**決定**: 設備からペルソナごとの表示を導出する際、○/△/✕の3段階ではなく、
「必要な行為」を言語化した6分類（そのまま通れる／係員を呼ぶ／畳んで抱える／
持ち上げる／駅員複数名の介助／通れない）を使う。

**コンテキスト**: 検証の過程で「エスカレーター＝ベビーカー可（△程度）」という解釈が
誤りであることが分かった。開発者指摘: 畳んで子どもを抱っこすればいい、というのは
その通りだが、双子連れや荷物が多い場合は現実的ではない。○/△/✕程度の粗さでは、
利用者本人が自分の状況で判断するための情報量が足りない。

**オプション**:
- (a) 6分類で「必要な行為」を言語化する（採用）
- (b) ○/△/✕の3段階に留める — 却下。「畳んで抱える」という条件付きの可否を、
      当事者以外が○か✕かに固定してしまう。

**理論的根拠**: 「何が必要か」という行為の記述は、可否の最終判断を利用者自身に委ねられる。

**影響**: 表示文言は「利用可能」ではなく「畳んで抱える必要があります」のような
行為の記述になる。この6分類のうち「そのまま通れる」「係員を呼ぶ」だけを
バリアフリールートとして扱う（REQ-15）。**「通れる」と「バリアフリーで通れる」は別物**で、
霞ケ関のベビーカー（階段を持ち上げれば通れるが、バリアフリールートは無い）を
正しく表示するにはこの2段の述語が必要である。

**レビュー**: 実装Issueで、実際の文言をユーザビリティの観点から確認する。

### 決定9 — 備考は残し、逃がし弁として位置づけを明記する

**決定**: 備考（接続単位・ルート単位）は廃止せず残す。ただし役割を
「モデルが構造的に表現しない次元の受け皿」に限定し、経路上の選好（決定1で排除した
情報）を書く場所ではないことを明記する。

**コンテキスト**: 開発者から「この設計・実装が終わるまで、今新御茶ノ水・淡路町に
書いてある備考情報を失いたくない」という要望があった。一方、決定1の検証で、
現行の備考には経路上の選好（「大手町のほうが便利」）も混入していることが判明した。

**オプション**:
- (a) 備考は残すが、役割を明記する（採用）
- (b) 備考を廃止し、全情報を軸で表現する — 却下。時間帯制約・工事中の仮設ルート・
      設備の質のように、軸を増やしても解決しない次元が実在する。
- (c) 備考をさらに構造化する（時間帯フィールド等を追加） — 却下。
      実データの蓄積が無い段階で頻度を見積もれず、過剰設計になる（Issue #120）。

**理論的根拠**: 備考を残すこと自体は正しいが、無定義であることが決定1の問題を
再発させる。

**影響**: 備考はペルソナ別ではなくなった（決定3でペルソナが層でなくなったため）。
ペルソナ別の備考に書かれていた内容は、ルート単位の備考か、設備の記録に移る。
既存16行の移行時、経由の選好に相当する記述（「大手町のほうが便利」）は削除する（Issue #123）。

**レビュー**: 備考に同種の記述が蓄積したら、構造化を再検討する。

### 決定10 — ルートの役割は種別ではなくフラグで持つ

**決定**: ルートに `kind = general | step_free` のような**種別**を持たせず、
`isBaseline`（一般利用者が案内される基準ルートか）という**役割フラグ**を持たせる。
基準ルートは接続あたり高々1本に制約する。

**コンテキスト**: 決定3でルートを行にしたとき、最初は「一般ルート」と
「バリアフリールート」を種別で二分する形を検討した。開発者から
「`general` / `step_free` がそれぞれ接続に対して1件である保証がない」との指摘があり、
検討したところ、種別による二分そのものが誤りだと判明した。

**オプション**:
- (a) 役割フラグ `isBaseline`（採用）
- (b) 種別 `kind = general | step_free` — 却下。明治神宮前のように一般利用者も
      同じエレベーターを通る駅では、**同じ物理経路を2行書く**ことになる。
      決定3で排除した重複が形を変えて戻る。さらに `kind` は
      「一般ルートが複数ある」「バリアフリールートが複数ある」の両方を許すため、
      迂回度の分母（決定6）が一意に定まらない。
- (c) 基準ルートの情報を接続側の列（`normalRouteMinutes` 等）に残す — 却下。
      基準ルートの設備・屋外・改札外が持てず、指摘D（高田馬場と御茶ノ水の区別）が
      解決しない。接続側にフラグ列を足すと、ルート行と同じ列を2箇所に持つことになる。

**理論的根拠**: 「一般利用者が案内される経路か」は経路の**役割**であって種類ではない。
1本の経路が同時にバリアフリールートでもある（明治神宮前）ことは普通に起こる。
役割をフラグにすれば、1行＝1経路の原則を崩さずに済む。

**影響**: 部分ユニークインデックス `(connectionId) where is_baseline` で
1本制約をDBに持たせられる。基準ルートの付け替えは「既存の降格＋新規の昇格」の2文に
なるため、Repository と `withTransaction` の担当になる（ADR-0005）。

再改訂（決定4）で `isBaseline` の置き場所が変わった。ルートが複数の接続から
共有されるようになったため、`isBaseline` はルート自体の属性ではなく、
**接続とルートの紐付け（`connection_routes`）の属性**になる。部分ユニークインデックスも
`connection_routes(connectionId) where is_baseline` に移る。役割がフラグである
という本決定の核（(a) vs (b)）は変わらないが、置き場所を対応させて読む必要がある。
これにより、同じ物理ルートが接続Xでは基準ルート、接続Yでは基準ルートでない、
という状態も構造上表現できる（通常は起きないが、モデルとしては禁止しない）。

**レビュー**: 基準ルートが不明な接続（一般ルートの所要時分が分からない駅）が
どの程度あるかを確認する。多い場合は「基準ルート無し」を許容する運用が要る
（現行の設計では 0本を許容しており、そのとき迂回度は導出できない）。

### 決定11 — ルートの識別は `label`、一意制約は属性に頼らない

**決定**: ルートの識別子は人間が付ける `label` とし、`unique (connectionId, label)` で
縛る。フラグ（`isOfficiallyGuided` 等）を一意キーに含めない。

**コンテキスト**: 開発者から「`transfer_routes` に一意制約がないのが気になる。
無限に追加し続けられるのもおかしい。`is_officially_guided` も使って一意制約を
つけられないか」との指摘があった。

**オプション**:
- (a) `label` を必須にし、`(connectionId, label)` で縛る（採用）
- (b) `(connectionId, isBaseline, isOfficiallyGuided)` 等、属性の組で縛る — 却下。
      西日暮里（公式の階段昇降機ルート＋非公式の改札外ルート）では実際に機能するが、
      ①事業者が案内を始めたときの `UPDATE` が既存行と衝突する（可変な属性を識別子に
      昇格させると、事実の訂正が制約に阻まれる）、②公式ルートが2本ある巨大駅のような
      将来の正当なデータを弾く、③4つのフラグのうち1つを選ぶ根拠がない
      （物理的な経路差をよく表すのは `requiresExitGate` のほう）。
- (c) 制約を付けず、重複はアプリ層だけで防ぐ — 却下。同じ経路を2回登録する事故を
      DBで止められない。
- (d) 設備の並びとフラグからハッシュを生成し、生成列に一意制約を張る — 却下。
      訂正のたびに識別子が変わり、外部からの参照が壊れる。過剰。

**理論的根拠**: 一意制約違反が「データが誤っている」ではなく「モデルが足りない」を
意味するようになると、入力者は制約を通すために事実を曲げる。`label` は可変でも
衝突せず（同一接続内で同名が2つできないだけ）、しかも表示で「どのルートか」を
示すのに必要な情報なので、識別と表示の二役を担う。

**影響**: `label` は `NOT NULL`。命名は入力者に委ねるが、Admin はプレースホルダで
実例（「北改札経由」「地上経由」）を示す。**行数の上限は制約では表現しない**
（PostgreSQL の制約は行数を数えられない）。同一経路の二重登録は、設備の並びと
4フラグの一致をアプリ層で検出して防ぐ（REQ-23。集合の一意性はDB制約で書けない）。

再改訂（決定4）で `label` の置き場所が変わった。`transfer_routes` が `connectionId`
を持たなくなったため、`unique(connectionId, label)` をそのままの形では張れない。
`label` を **`connection_routes`（接続とルートの紐付け）に非正規化**し、一意制約も
そちらに置く。同一の物理ルートが複数の接続から参照されるとき、各接続での呼び名
（`label`）は独立して構わない（通常は同じ名前を使うのが自然だが、モデルとして
一致を強制しない）。これは決定4のオプション(d)を選んだことの直接の帰結であり、
「識別と表示の二役を `label` が担う」という本決定の理論的根拠は変わらない。

**レビュー**: 「ルート1」「ルート2」のような無意味な `label` が入り始めたら、
命名規約か候補の提示を検討する。#122 のスキーマ実装で、`connection_routes` への
`label` 非正規化が drizzle-orm で自然に表現できるか確認する。

### 決定12 — 複数ルートは並記し、並べ替えは所要時分のみで行う

**決定**: あるペルソナにバリアフリールートが2本以上あるとき、すべてを並記する。
並べ替えキーは `minutes` の昇順のみとし、「必要な行為」で並べない。
「おすすめ」に相当する印を付けない。

**コンテキスト**: 決定3で複数ルートを持てるようになった結果、表示側に
「どれを先に見せるか」という問題が生じた。西日暮里の車いすの2択
（係員を呼んで6分 / 自力で屋外13分）がその実例である。

**オプション**:
- (a) 所要時分の昇順のみ（採用）
- (b) 必要な行為の軽い順 — 却下。「畳んで抱える」と「係員を呼ぶ」のどちらが軽いかは
      利用者によって逆転する。これは決定8がまさに避けた判断である。
- (c) 「おすすめ」を1本選んで先頭に置く — 却下。決定1に反する。
      どのルートが良いかは利用者の事情（雨天か、時間に余裕があるか、
      駅員を待てるか）で決まる。

**理論的根拠**: `minutes` は客観値であり、順序が入力者の主観に依存しない。
並べる順序自体が推奨のシグナルになり得るため、キーは客観値に限る必要がある。

**影響**: 表示は4状態に分岐する（REQ-16）。とくに「バリアフリールートなし」は、
現行の `inaccessible`（「エレベータールートが整備されていない」）の代替であり、
未評価（ルート0本）と明確に区別して表示する。複数表示では、値が共通する項目を
繰り返さず、異なる項目（屋外・係員・所要時分・公式案内）を強調する。

**レビュー**: 実装Issueで、3本以上のルートを持つ接続の表示が煩雑になっていないか確認する。

## この定義の引き継ぎ先

`docs/spec/` の3点セットは次のIssueで全面書き換えられる。本Issueは定義のみで
実装を伴わないため、`docs/domain/` の更新は本Issueでは行わない
（ワークフロー上、フェーズ5＝実装後に行う）。実装Issueのフェーズ5で、以下を
`docs/domain/station-master-model.md`（「乗換接続（`stationConnections`）」節）に
反映すること。

- 4層構造（接続 → 接続とルートの紐付け → ルート → 設備）と、ペルソナが層ではないこと
  （決定2・3）。ルートは接続に従属せず、`connection_routes` で多対多に結ばれること
- 評価の単位が方面×方面になったこと。方面の値域は `direction_type`
  （`'inbound' | 'outbound'`）であり `line_directions.id` ではないこと。両端点とも
  必須で `NULL` を許容しないこと。優先順位規則・タイブレークは無く、完全一致の1行を
  引くだけで解決すること（REQ-2・3）
- 全方面共通の表現は、方面の組み合わせ分の接続それぞれが同一のルートを共有すること
  （決定4）。REQ-23（同一経路の二重登録防止）の検出は接続をまたいで行うこと
- `label` と `isBaseline` は `transfer_routes` ではなく `connection_routes`
  （接続とルートの紐付け）に属すること（決定10・11）
- 無向1行への正規化（決定5）と、読み取り側が両方向を見る必要があること
  （`stationAdjacencies` の記述パターンに倣う）
- 不変条件とその守り方（「不変条件」節の表をそのまま移す）。方面が両端点とも
  `NOT NULL` のため `NULLS NOT DISTINCT` は不要であること。部分ユニークインデックスは、
  外そうとする人が必ず見る場所に理由を添えて置くこと
- 設備の並びは直列のみを表し、同じ段差の代替手段は別ルートになるという帰属規則
- 「通れる」と「バリアフリーで通れる」が別の述語であること（決定8・REQ-15）
- `source` 由来の記述（`ekidata_group` / `manual` / `NULL`）は、方面粒度化の影響を
  受けない。1つのホーム対に対する行の由来という点は変わらないため、そのまま維持する
- 「難易度・備考は両方向に同じ値が入る」という現行の記述は、無向1行化により
  「両方向に同じ値を書く」という運用そのものが不要になるため、削除して書き換える
- 備考の役割（決定9: 逃がし弁として何を書き、何を書かないか）
- `direction_type` は乗換単位（物理ホーム）を一意に決めないこと（分岐駅・二重通過駅・
  直通分岐では同じ `(駅, 方面)` に複数ホームが対応しうる）。中野坂上型は
  [Issue #128](https://github.com/Natsugure/furatora/issues/128)（丸ノ内線支線の
  復元）を前提とした既知の制約であること（決定4）

`docs/domain/` へ移す判断基準に照らすと、上記はすべて「次のIssue以降も有効であり続ける
恒久知識」（不変条件・ドメインルールに相当）であり、`docs/spec/` に置き去りに
してはならない。この節と、`tasks.md` の `docs/domain/` 反映タスクが、実装Issueへの
引き継ぎ手段になる。
