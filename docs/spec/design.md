# 設計: 乗り換え難易度定義の改善 (Issue #30)

## 参照

[requirements.md](./requirements.md) / [tasks.md](./tasks.md) /
[docs/domain/station-master-model.md](../domain/station-master-model.md)（現行モデル。
「乗換接続（`stationConnections`）」節）/ [ADR-0003](../adr/0003-read-write-separation.md)
（difficulty からラベル・色を決める変換をDTOの責務としない、という既存決定）

## モデル

### 評価の単位

**無向のホーム方面対。** 端点は `(stationId, directionId | NULL)`。

`stations` は路線×駅粒度なので `stationId` が路線を含意する（`docs/domain/
station-master-model.md`「駅の粒度」）。`directionId` は `line_directions.id` を参照し、
`NULL` は「全方面共通」を表す。

端点を昇順に正規化して1行で持つ。方式は既存の `stationAdjacencies` と同じ
（`apps/admin/src/features/station-adjacency/domain/normalize.ts` の
`normalizeAdjacencyEndpoints()` を参考にする。当該関数は隣接専用の実装だが、
「端点を正規化して無向1行にする」という考え方は共有できる）。

```
端点A: (淡路町/丸ノ内線, 池袋方面)   端点B: (小川町/都営新宿線, NULL)
端点A: (淡路町/丸ノ内線, 荻窪方面)   端点B: (小川町/都営新宿線, NULL)
端点A: (後楽園/丸ノ内線, NULL)       端点B: (春日/都営三田線, NULL)   ← 大半はこの形
```

### 解決規則（REQ-8）

問い合わせは常に `(stationA, directionA?, stationB, directionB?)` で行う。

1. 方面が一致する行があれば、それを使う。
2. 無ければ、両端点を `NULL` に落とした行（全方面共通）を使う。
3. どちらも無ければ、未評価として扱う（現行と同じ。難易度は任意入力）。

淡路町↔小川町のように一部方面だけ例外がある駅では、例外行だけを追加すればよく、
大半の駅は `NULL` 行1件で足りる。

### 保持する事実

**接続に1つ（ペルソナ非依存）**

| フィールド | 型 | 意味 |
|---|---|---|
| `normalRouteMinutes` | 数値（分） | 一般利用者の乗換所要時分 |
| `notes` | 自由記述 | ペルソナ非依存の備考 |

**ペルソナごと（`stroller` / `wheelchair`）**

| フィールド | 型 | 意味 |
|---|---|---|
| `stepFreeVia` | 名義尺度7値 | バリアフリールート上の最弱リンク |
| `routeMinutes` | 数値（分） | そのペルソナの乗換所要時分 |
| `isOutdoor` | 真偽 | 屋外を通るか |
| `requiresExitGate` | 真偽 | 改札外を経由するか |
| `requiresStaff` | 真偽 | 係員対応が必要か |
| `notes` | 自由記述 | ペルソナ別の備考 |

`stepFreeVia` の7値: `same_floor` / `elevator` / `ramp` / `wheelchair_escalator` /
`escalator` / `stair_lift` / `stairs`。

既存の `facility_types`（`elevator` / `escalator` / `ramp` / `sameFloor` /
`stairLift` / `stairs`）とほぼ同じ語彙を採用する。追加が必要なのは
`wheelchair_escalator`（車いす対応・係員操作のエスカレーター）のみで、淡路町の実データ
「丸ノ内線 荻窪方面と都営新宿線間はエレベーターのみで乗り換え可能です」に対し、
池袋方面の備考「途中車いす対応エスカレーターを使う必要があります」が要求している。
なお `ramp` と `stairLift` は `facility_types` に定義済みだが、`station_facilities`
の実データは0件（未実測の値）。

### 導出する値（表示層の純粋関数。保存しない）

`stepFreeVia` → 必要な行為（REQ-11〜14）:

| `stepFreeVia` | ベビーカー | 車いす |
|---|---|---|
| `same_floor` / `elevator` / `ramp` | そのまま通れる | そのまま通れる |
| `escalator` | 畳んで抱える必要 | 通れない |
| `wheelchair_escalator` | 畳んで抱える必要 | 係員を呼ぶ必要 |
| `stair_lift` | **通れない** | **係員を呼ぶ必要** |
| `stairs` | 持ち上げる必要 | 駅員複数名の介助が必要 |

`normalRouteMinutes` とペルソナの `routeMinutes` の差・比 → 迂回度（REQ-15）。

変換は ADR-0003 の既存決定（「difficulty から表示色やラベルを決める変換はDTOの責務では
ない」）に合わせ、表示層に置く。現行の `apps/web/src/constants/difficulty.ts` /
`apps/admin/src/constants/difficulty.ts` と同じ位置づけになる。

### 持たないもの

| 対象 | 理由 / 行き先 |
|---|---|
| おすすめ度・合理性・推奨乗換駅 | 出発地・目的地に依存し、接続単体の属性にできない（決定1） |
| 方面粒度で救えない方向依存（上り専用エスカレーター等） | 備考（決定9） |
| 設備の質（EVのサイズ、スロープの勾配） | 備考（決定9） |
| 時間帯制約（早朝深夜のEV停止）、工事中の仮設ルート | 備考（決定9） |

## 決定記録

いずれも既存ADRの決定に反しない（ADR-0003 の DTO 責務分離方針を踏襲する形）ため、
新規ADRは作成しない。乗換難易度というドメインのモデル化そのものの決定であり、本文書に
決定記録として残す。

### 決定1 — 接続は事実のみを持ち、推奨・合理性を持たない

**決定**: 乗換難易度は出発地・目的地に依存しない接続の事実のみを保持し、
「どの乗換駅を使うべきか」「この接続は推奨できるか」は保持しない。

**コンテキスト**: 現行の `discouraged`（「可能だが非合理的で推奨できない」）や
実データの備考「隣の大手町駅のほうが便利です」は、出発地・目的地が決まって初めて言える
経路上の選好を、接続の属性として断定している。有楽町線↔副都心線の池袋駅の例
（要町の接続パラメータ自体は良好でも、東池袋方面↔雑司が谷方面間の乗り換えに要町を
案内すると折返し乗車になるため案内できない）は、良し悪しが接続の外側（出発地・目的地・
進行方向）で決まることを示す。

**オプション**:
- (a) 事実のみ保持し、推奨・合理性は持たない（採用）
- (b) 事実に加え、接続単体の「おすすめ度」を人手で付与する列も持つ
  — 却下。要町の例のように、接続単体では正しい可否と、経路全体で見た案内可否が
  食い違う場合に、どちらが正なのか規則が要る。矛盾する二つの真実を同居させるだけになる。
- (c) 経路探索の設計を先にやり、そこから逆算して接続が持つべき属性を決める
  — 却下。手戻りは少ないが、未実装の機能の設計が本Issueより先行し、スコープが膨らむ。

**理論的根拠**: (b) は要町のケースで矛盾した状態を作れてしまう。「どの乗換駅を使うべきか」
は接続そのものの属性ではなく、出発地・目的地・進行方向を入力に取る別の計算
（経路探索）の出力である。

**影響**: 推奨乗換駅の判定機能は、本Issueでは実装されない。将来の経路探索機能で
本モデルの事実（`stepFreeVia` / `routeMinutes` / 3フラグ）を入力として解く。

**レビュー**: 経路探索機能の設計時に、本モデルの事実だけで十分かを再確認する。

### 決定2 — 値域は設備の名義尺度、ペルソナ別の可否は導出する

**決定**: `stepFreeVia` は「どの設備を通るか」を表す名義尺度（順序を持たない）とし、
ペルソナごとの可否・必要な行為は表示層の変換関数で導出する。

**コンテキスト**: エスカレーターと階段昇降機で、2ペルソナの可否が逆転する。
階段昇降機はベビーカーが使えず（固定用の台で、通れない）、車いすは係員操作で使える
（三田駅: 浅草線↔三田線）。一般的なエスカレーターは車いすが使えず、ベビーカーは
畳んで抱えれば使える（ただし双子連れ・多荷物では現実的でない — 開発者指摘。
「○/△/✕」の3段階も粗すぎ、必要な行為を言語化する REQ-11〜14 の5分類に至った）。

**オプション**:
- (a) 値域を設備の名義尺度にし、可否は導出する（採用）
- (b) 値域を「ペルソナごとの可否」（可能 / 係員対応で可能 / 不可能）にし、人手で入力する
  — 却下。同じ設備について2回（ベビーカー用・車いす用）判断が必要になり、
  「なぜそうなのか」という事実（階段昇降機だから、という理由）が備考にしか残らない。
  さらに検証中、「エスカレーター＝ベビーカー可」という解釈自体を訂正する必要が生じた。
  事実（設備）を保存していたため変換関数1箇所の修正で済んだが、可否を直接保存する
  設計であれば入力済みの全行を洗い直す必要があった。
- (c) 単一の順序尺度（1軸5段階）にする — 却下。エスカレーターと階段昇降機の可否逆転を
  単一の順序で表現することはできない（どちらを「重い」側に置いても片方が壊れる）。
  現行スキーマが2ペルソナ別の enum を持っているのは、この逆転を2本の尺度に分けて
  回避した結果であり、値域の統一そのものが不可能だと判明した。

**理論的根拠**: (a) は事実と解釈を分離するため、解釈の誤りが訂正コストの低い箇所
（変換関数）に閉じる。(b)(c) は事実と解釈を融合するため、解釈の誤りがデータ全体に
波及する。

**影響**: `stepFreeVia` の変換関数（表示層）は、ペルソナごとの解釈規則を1箇所に
集約する。将来、解釈基準が変わっても（例: エスカレーターの許容判断が事業者の
ガイドライン変更で変わる）、データを触らず関数だけ直せばよい。

**レビュー**: 変換関数の実装時に、REQ-11〜14 の表を1対1でテストする。

### 決定3 — 列（行）はペルソナごとに分ける

**決定**: `stepFreeVia` / `routeMinutes` / 3フラグは、`stroller` / `wheelchair`
それぞれに個別の値として持つ（1組の値をペルソナ間で共有しない）。

**コンテキスト**: 三田駅（浅草線↔三田線）では、ベビーカーの経路は階段
（`stepFreeVia = stairs`）、車いすの経路は階段昇降機（`stepFreeVia = stair_lift`）で、
物理的に異なる経路をたどる。同一設備についての解釈違いではなく、経路そのものが
ペルソナで分岐している。

**オプション**:
- (a) `stroller` / `wheelchair` を別々の値として持つ（採用）
- (b) 軸を1組だけ持ち、ペルソナ間で共通の値とする — 却下。三田駅の例で経路自体が
  分岐する場合に表現できない。
- (c) 値は1組だが、経路が分岐する接続だけ備考で説明を加える — 却下。三田駅のような
  逆転が構造的に起きうる（エスカレーター系設備が絡む接続すべて）ため、例外処理ではなく
  モデルの基本形にすべきと判断した。

**理論的根拠**: 三田駅は「稀な例外」ではなく、決定2の逆転（エスカレーター系と
階段昇降機の可否逆転）が起きる接続では構造的に発生する。値を1組にすると、
そのたびに備考への逃避が必要になり、決定1・3の目的（事実を軸で表現する）に反する。

**影響**: 接続1行あたりの列数は増える（ペルソナ非依存1軸 + ペルソナ別5軸×2）。
1つのホーム対に対する入力は最大10項目になるが、大半の接続は両ペルソナで同じ値
（後楽園↔春日など）になるため、入力側でコピー機能を用意すれば負担は抑えられる
（実装Issueでの検討事項）。

**レビュー**: 実データで両ペルソナの値が一致する接続の割合を確認し、コピー機能の
必要性を判断する。

### 決定4 — 粒度は方面×方面、`NULL` は全方面共通

**決定**: 評価の単位は駅×駅ではなく方面×方面とし、方面を指定しない行（`NULL`）を
「全方面共通」として許容する。

**コンテキスト**: 淡路町↔小川町では丸ノ内線の方面によって条件が異なる
（池袋方面は途中階段、荻窪方面はエレベーターのみ）。都営浅草線・新宿線・日比谷線にも
方面別に条件が異なる駅が多数あるとの開発者指摘があった。当初は駅×駅の粒度維持を
決定していたが、この指摘を受けて撤回した。

**オプション**:
- (a) 方面×方面、`NULL` 許容（採用）
- (b) 番線×番線（`platforms` テーブル） — 却下。`platforms` は実データで20駅40行しか
      登録されておらず（公開駅334件に対し登録率が低い）、難易度を書く前に番線登録が
      必須という制約が強すぎる。
- (c) 方面×方面を必須とする（`NULL` を許容しない） — 却下。大半の駅は方面差が無く、
      毎回2×2=4行を手で埋めることになり入力コストが跳ね上がる。

**理論的根拠**: (a) は大半の駅（方面差の無い駅）を `NULL` 1行で表現でき、
淡路町のような例外だけ具体的な行を追加すればよい。(b) は前提となるデータ整備が
本Issueの射程を超える。(c) は入力コストと粒度のバランスを欠く。

**影響**: 評価の解決に優先順位規則（REQ-8。具体的な行 → `NULL` 行）が必要になる。
`line_directions` テーブルへの参照が増える。

**レビュー**: 番線（`platforms`）の登録が進んだ段階で、番線粒度への昇格が必要かを
再検討する。

### 決定5 — 向きは無向1行に正規化する

**決定**: 評価は無向として、端点を正規化した1行で保持する。現行の「有向2行に同じ値を
入れる」運用は廃止する。

**コンテキスト**: 決定4で方面を導入すると、有向2行の運用が成立しなくなる。
淡路町→小川町（池袋方面から本八幡方面へ）の逆方向は、「小川町の新宿方面ホーム →
淡路町の荻窪方面ホーム」であり、**同じホーム対ではない**。値をコピーできない。
一方、同じホーム対の往復（P→Q と Q→P）は通常同じ経路なので、無向1行にまとめられる。

**オプション**:
- (a) 無向、端点を昇順正規化した1行（採用）
- (b) 有向2行を維持する — 却下。方面を入れた場合コピーできる前提が崩れ、
      全行を独立に手入力することになり、決定4で方面を導入した目的（少ない入力で
      例外だけ表現する）と矛盾する。

**理論的根拠**: `stationAdjacencies`（隣接）が同じ問題を「無向1行・端点昇順正規化・
読み取り側が両方向を見る」で解決した前例がある。同じ方式を採用することで、
プロジェクト内の一貫性も保てる。

**影響**: 読み取り側は端点の両順序（A,B）と（B,A）を見る必要がある。書き込み側は
INSERT前に正規化関数を通す必要がある（実装Issueで `normalizeAdjacencyEndpoints()`
に類する関数を用意する）。上り専用エスカレーターのような、往復で経路が異なる稀な
ケースは無向のモデルでは表現できず、備考に落ちる（決定9）。

**レビュー**: 往復で経路が異なるケースの実例が一定数見つかった場合、有向化を再検討する。

### 決定6 — 迂回度は持たず、2つの所要時分から導出する

**決定**: 「迂回度」という軸を直接保存せず、`normalRouteMinutes` とペルソナ別
`routeMinutes` の差・比から導出する。

**コンテキスト**: Issue #30 が提案する4軸の一つ「迂回度合」を、時分軸と独立に
持つべきか検討した。「小/中/大」のような人手判定の順序尺度は、判定基準が
言語化されないまま入力者ごとにブレる恐れがある。

**オプション**:
- (a) 迂回度は持たず、2つの時分から導出する（採用）
- (b) 独立した順序尺度として人手入力する — 却下。基準が言語化できず
      （「12分ならどの段階か」に答えがない）、入力者間でブレる。
- (c) 迂回度を持たず、時分のみ持つ（差・比の導出もしない） — 却下。
      「一般ルートと比べてどれだけ迂回するか」は利用者にとって意味のある情報であり、
      REQ-15 で導出さえすれば追加の保存コストなく提供できる。

**理論的根拠**: 2つの時分を持てば迂回度は数値として一意に決まり、主観的な判定基準を
作らずに済む。経路探索機能にとっても、時分は迂回度より直接使いやすい入力になる。

**影響**: 「迂回度」という言葉は表示層のラベルとしてのみ残り、保存されるフィールドは
時分2つになる。

**レビュー**: 実装Issueで、後楽園↔春日（改札内3分／改札外経由で大回り）のような
実例を使って導出結果が妥当か確認する。

### 決定7 — 4軸目を屋外・改札外・係員の3フラグに分解する

**決定**: Issue #30 の4軸目「屋外乗り換え・係員対応の必要性」を、独立した3つの真偽値
（`isOutdoor` / `requiresExitGate` / `requiresStaff`）に分解する。

**コンテキスト**: 実例を洗い出すと、3つが独立に組み合わさるケースが実在する。

| 実例 | 屋外 | 改札外 | 係員 |
|---|---|---|---|
| 御茶ノ水 | ○ | ○ | ✕ |
| 後楽園↔春日 | ✕（屋内） | ○ | ✕ |
| 三田 | ✕ | ✕（改札内） | ○ |

**オプション**:
- (a) 3つの独立フラグに分解する（採用）
- (b) Issue記載どおり1軸にまとめる — 却下。上表のとおり全パターンが実在し、
      1軸では後楽園↔春日（改札外だが屋内）と三田（改札内だが係員必須）を
      区別できない。

**理論的根拠**: 3つが独立変数であることが実データで確認できた以上、1軸にまとめると
情報が失われる。

**影響**: `requiresStaff` は決定2の `stepFreeVia`（`stair_lift` / `wheelchair_escalator`
は必ず係員操作）と相関するが、乗換改札が車いす非対応で係員呼出が必要になるような、
設備と無関係に発生するケースもあるため、独立フラグとして残す。

**レビュー**: 実装Issueで、`stepFreeVia` から `requiresStaff` が導出できる場合と
できない場合の切り分けを確認する。

### 決定8 — 表示は「何が必要か」の5分類を導出する

**決定**: `stepFreeVia` からペルソナごとの表示を導出する際、○/△/✕の3段階ではなく、
「必要な行為」を言語化した5分類（そのまま通れる／畳んで抱える／持ち上げる／
係員を呼ぶ／通れない）を使う。

**コンテキスト**: 検証の過程で「エスカレーター＝ベビーカー可（△程度）」という解釈が
誤りであることが分かった。開発者指摘: 畳んで子どもを抱っこすればいい、というのは
その通りだが、双子連れや荷物が多い場合は現実的ではない。○/△/✕程度の粗さでは、
利用者本人が自分の状況で判断するための情報量が足りない。

**オプション**:
- (a) 5分類で「必要な行為」を言語化する（採用）
- (b) ○/△/✕の3段階に留める — 却下。上記の指摘のとおり、「畳んで抱える」という
      条件付きの可否を、当事者以外が○か✕かに固定してしまう。

**理論的根拠**: 「何が必要か」という行為の記述は、可否の最終判断を利用者自身に
委ねられる。5分類は決定2の変換関数（REQ-11〜14）の出力そのものであり、
追加の実装コストは発生しない。

**影響**: 表示文言は「利用可能」ではなく「畳んで抱える必要があります」のような
行為の記述になる。

**レビュー**: 実装Issueで、実際の文言をユーザビリティの観点から確認する。

### 決定9 — 備考列は残し、逃がし弁として位置づけを明記する

**決定**: `notes`（ペルソナ非依存・ペルソナ別）は廃止せず残す。ただし役割を
「モデルが構造的に表現しない次元の受け皿」に限定し、経路上の選好（決定1で排除した
情報）を書く場所ではないことを明記する。

**コンテキスト**: 開発者から「この設計・実装が終わるまで、今新御茶ノ水・淡路町に
書いてある備考情報を失いたくない」という要望があった。一方、決定1の検証で、
現行の備考には経路上の選好（「大手町のほうが便利」）も混入していることが判明した。
備考を無定義のまま残すと、この混入が再発する。

**オプション**:
- (a) 備考は残すが、役割を明記する（採用）
- (b) 備考を廃止し、全情報を軸で表現する — 却下。時間帯制約・工事中の仮設ルート・
      設備の質（EVサイズ等）のように、軸を増やしても解決しない次元が実在する
      （REQ-6・REQ-7で拾えるのは屋外・改札外・係員・方面のみ）。
- (c) 備考をさらに構造化する（時間帯フィールド等を追加） — 却下。
      実データの蓄積が無い段階で頻度を見積もれず、過剰設計になる。

**理論的根拠**: 備考を残すこと自体は正しいが、無定義であることが決定1の問題を
再発させる。役割を明記すれば、既存の御茶ノ水・淡路町の記述はそのまま活かせる。

**影響**: 実装Issueで、既存16行の備考を新モデルに移行する際、経由の選好に相当する
記述（「大手町のほうが便利」）は備考から削除し、軸（決定1の対象外）または
GitHub Issue（先送りした将来作業）に移す。

**レビュー**: 備考に同種の記述（頻度の高いパターン）が蓄積したら、構造化
（決定9-(c)）を再検討する。

## この定義の引き継ぎ先

`docs/spec/` の3点セットは次のIssueで全面書き換えられる。本Issueは定義のみで
実装を伴わないため、`docs/domain/` の更新は本Issueでは行わない
（ワークフロー上、フェーズ5＝実装後に行う）。実装Issueのフェーズ5で、以下を
`docs/domain/station-master-model.md`（「乗換接続（`stationConnections`）」節）に
反映すること。

- 評価の単位が方面×方面（`NULL` 許容）になったこと、解決規則（REQ-8）
- 無向1行への正規化（決定5）と、読み取り側が両方向を見る必要があること
  （`stationAdjacencies` の記述パターンに倣う）
- `source` 由来の記述（`ekidata_group` / `manual` / `NULL`）は、方面粒度化の影響を
  受けない。1つのホーム対に対する行の由来という点は変わらないため、そのまま維持する
- 「難易度・備考は両方向に同じ値が入る」という現行の記述は、無向1行化により
  「両方向に同じ値を書く」という運用そのものが不要になるため、削除して書き換える
- 備考の役割（決定9: 逃がし弁として何を書き、何を書かないか）

`docs/domain/` へ移す判断基準に照らすと、上記はすべて「次のIssue以降も有効であり続ける
恒久知識」（座標系・不変条件・ドメインルールに相当）であり、`docs/spec/` に置き去りに
してはならない。この節と、`tasks.md` の `docs/domain/` 反映タスクが、実装Issueへの
引き継ぎ手段になる。
