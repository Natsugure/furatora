# 要件: 乗換難易度 Web 表示の対応 (Issue #125)

## 概要

- **対象**: Web の駅詳細にある乗換セクション（`TransferDifficultySection`）を、`station_connections` の旧4列から
  新モデル（接続 → ルート → 設備）に切り替える。ペルソナごとの必要な行為は、設備から表示層で導出する
- **参照**: [design.md](./design.md) / [tasks.md](./tasks.md) /
  [Issue #125](https://github.com/Natsugure/furatora/issues/125) /
  `docs/domain/station-master-model.md`「乗換難易度」/ `docs/domain/line-directions.md` /
  ADR-0003・0011・0012・0014 / #30 時点の要件（`git show 3c2fa0c:docs/spec/requirements.md` の REQ-13〜19）
- **ブランチ**: `feat/issue125-transfer-difficulty-web`
- **信頼度**: 80%（中）。導出規則は #124 のパッケージにあり、方面ラベルは #130 で解決済み。
  不確実性は表示の見せ方（状態の文言・方面の見出し）だけなので、MVP を開発者が development で確認してから仕上げる

## 背景

#124 から、Admin は旧4列（`strollerDifficulty` / `wheelchairDifficulty` / `notesAbout*`）を書かない。
旧4列の値は #123 の移行時点のまま凍結されている。Web がまだ旧4列を読むため、新モデルで入力した内容が Web に出ない。

Issue 本文・コメントとの読み替え:

| Issue 本文 | 本書での扱い |
|---|---|
| 変換関数を `apps/web/src/constants/difficulty.ts` の位置に置く | 導出関数は `@furatora/transfer-difficulty/domain` にある（#124）。重さの順序を使う関数（最も軽い行為・状態の分類）もパッケージに足す |
| 「経路上の直列な設備」 | 「ルート上の設備の**種類の集合**」（ADR-0011） |

| `line_directions.isDefault` がブロッカー | #130 で解決済み。`resolveDirectionLabel` を使う |

## 用語

- **自駅 S / 相手駅 T**: 表示中の駅と、乗換先の駅。
- **組み合わせ**: `(S の走行方向, T の走行方向)`。最大4通り。接続行は組み合わせごとに0行か1行。
- **バリアフリールート**: 必要な行為が「そのまま通れる」または「係員を呼ぶ」であるルート。
- **設備未入力のルート**: 設備が0件のルート（ADR-0012）。
- **基準ルート**: 接続とルートの紐付けで `isBaseline` が真のもの。

## 要件（EARS記法）

### 読み取り

- **REQ-1**: 駅詳細を表示するとき、システムは新モデルの接続・ルート・設備を読み、旧4列を読まないこと。
- **REQ-2**: システムは DTO でルートと設備をそのまま運び、ペルソナで絞り込まないこと（#30 REQ-19）。
- **REQ-3**: 接続を読むとき、システムは端点の両順序（S が A 側・B 側）を見ること。
- **REQ-4**: システムは乗換先の一覧に、接続行が1つも無い相手駅（未評価）も含めること。

### 導出（表示層の純粋関数）

- **REQ-5**: システムはルートごとの必要な行為を `requirementFor` で導出し、設備0件のルートについては導出しないこと。
- **REQ-6**: 組み合わせとペルソナが与えられたとき、システムは次のとおり状態を分類すること。

  | 状態 | 条件 |
  |---|---|
  | 未評価 | ルートが0本 |
  | バリアフリールートあり（単一／複数） | バリアフリールートが1本以上 |
  | 確認できていない | バリアフリールートが0本で、設備未入力のルートが1本以上 |
  | バリアフリールートなし | バリアフリールートが0本で、全ルートの設備が入力済み |

- **REQ-7**: 「確認できていない」と「バリアフリールートなし」の場合、システムは設備が入力済みのルートのうち、
  通行可能なもの（「通れない」以外）で最も軽い行為を示すこと。「確認できていない」では、確認できているルートに
  限った値である旨を添えること。「バリアフリールートなし」でそのようなルートが無ければ、その旨を示すこと。
- **REQ-8**: バリアフリールートを並べるとき、システムは所要時分の昇順でのみ並べ、所要時分が未入力のルートを末尾に置くこと。
  必要な行為で並べ替えないこと。「おすすめ」に相当する印を付けないこと。
- **REQ-9**: 基準ルートとバリアフリールートの最短の所要時分の両方があるとき、システムは
  「バリアフリールートの最短 − 基準ルート」を迂回度として導出し、必要な行為と並べて示すこと。
  どちらかが欠ける場合、迂回度を示さないこと。
- **REQ-10**: バリアフリールートが2本以上の場合、システムは、ルートの間で値が異なる項目（所要時分・必要な行為・4フラグ）を強調すること。

### 表示

- **REQ-11**: 評価済みの相手駅が1つも無い駅では、システムは乗換セクションを表示しないこと。
- **REQ-12**: 未評価の相手駅を選んだとき、システムは情報が無いことを示すこと。
- **REQ-13**: システムはベビーカーと車いすの状態を2列に並べて表示すること（現行の見た目を維持する）。
- **REQ-14**: 組み合わせの間でルートの組または接続の備考が異なる場合、システムは組み合わせをまとめたグループごとに、
  方面の見出しを付けて表示すること。すべての組み合わせが同じなら、見出しを付けないこと。
  評価済みの組み合わせと未評価の組み合わせが混在する場合、未評価の組み合わせを1つのグループとして示すこと。
- **REQ-15**: 方面の見出しの文言は `resolveDirectionLabel` で解決すること（① ホーム → ② 既定行 → ③ 上り/下り）。
- **REQ-16**: システムは各ルートについて、ルート名・所要時分（ある場合）・必要な行為・4フラグ・備考を示すこと。
  「公式案内なし」は、駅の構内図や公式の案内に載っていないルートである旨が伝わる文言にすること。
- **REQ-17**: 設備未入力のルートについて、システムは「そのまま通れる」と表示しないこと。
  システムは設備未入力のルートの有無・件数・名前を利用者に示さないこと
  （補完は管理者の作業であり、Admin で一覧する。[#135](https://github.com/Natsugure/furatora/issues/135)。開発者判断 2026-09-28）。
