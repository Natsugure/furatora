# 要件: 乗換難易度 Admin 入力フォームの対応 (Issue #124)

## 概要

- **対象**: Admin の乗換難易度の入力を、旧 `station_connections` の難易度4列から、新モデル
  （`transfer_connections` → `connection_routes` → `transfer_routes` → `transfer_route_facilities`）へ切り替える。
  (1) 駅対を単位とする編集画面と保存 API・Repository、(2) 設備から必要な行為を導出する純粋関数の
  共有パッケージ、(3) 旧4列を書く Admin の入力 UI・API の撤去。
  Web 表示（#125）と旧4列そのものの削除（#125 のあとの別デプロイ）は対象外
- **参照**: [design.md](./design.md) / [tasks.md](./tasks.md) /
  [Issue #124](https://github.com/Natsugure/furatora/issues/124) /
  ドメイン定義は `docs/domain/station-master-model.md`「乗換難易度」節 /
  [ADR-0011](../adr/0011-transfer-route-facilities-as-set.md)・[ADR-0012](../adr/0012-zero-facility-route-as-not-entered.md)
- **ブランチ**: `feat/issue124-transfer-difficulty-admin-form`
- **信頼度**: 80%（中）。永続化の規則（正規化・不変条件・トランザクション）は #122・#123 で確定していて不確実性は低い。
  不確実なのは**編集画面の使い勝手**（方面の組み合わせとルートの共有を、入力者が迷わず扱えるか）。
  中信頼度のため、編集画面の読み込み・保存を先に作り（MVP）、development で開発者が操作感を確認してから
  重複検出・共有バッジ・プレビューを足す

## 背景

#122 で新モデルのスキーマが、#123 で評価済み15駅対（接続60・ルート21）が入った。新モデルを読み書きする
コードはまだ無く、Admin は旧4列を編集している。#123 の移行データは、設備が未入力のルート
（設備0件。ADR-0012）や所要時分 `NULL` を多く含み、Admin での補完が前提になっている。
また、旧行に無かった13駅対は未評価のままで、新規入力が要る。

#124 の Issue 本文は #30 の改訂前の記述を含む。本書は次のとおり読み替える。

| Issue 本文 | 本書での扱い |
|---|---|
| 設備の並びを直列順で入力（追加・削除・並べ替え） | 設備は**種類の集合**（ADR-0011）。7種のチェックボックス。並べ替えは無い |
| 設備の並びと4フラグが一致したら保存を中断し、接続をまたいで検出 | **提示に弱め、範囲を同じ駅に限る**（REQ-15。池袋の6駅対が矛盾するため。design.md 決定2） |
| 基準ルートの付け替えを1トランザクションで | 駅対の保存が1トランザクションで、紐付けを入れ直す（REQ-13） |

## 用語

- **駅対**: 編集対象の乗換接続。自駅 S と相手駅 T（`station_connections` の1ペア）。
- **方面の組み合わせ**: `(S の方面, T の方面)`。`inbound` / `outbound` の 2×2 で**4通り**。1通りにつき
  `transfer_connections` の1行が対応する。
- **ルートカード**: 編集画面で1本のルートを編集する単位。1枚が、1本の `transfer_routes` と、
  適用先の方面の組み合わせごとの `connection_routes` 行に対応する。
- **共有中のルート**: 編集中の駅対の外の接続からも参照されているルート（例: 御茶ノ水の快速・各停）。
- **候補ルート**: 重複検出の比較対象。S か T を端点に持つ接続に結ばれたルートのうち、編集中の駅対に
  結ばれていないもの。

## 要件（EARS記法）

### 編集画面の対象と入口

- **REQ-1**: 駅の編集画面の乗換接続の各カードから、その駅対の乗換難易度の編集画面を開けること。
  編集画面は駅対（自駅 S・相手駅 T）を単位とし、方面の4通りの接続とそのルートを1画面で編集できること。
- **REQ-2**: 編集対象の駅対（`station_connections` の S→T）が存在しない場合、システムは編集画面を表示せず、
  保存を 404 で拒否すること。
- **REQ-3**: 編集画面を開くとき、システムは駅対の既存のルートを、ルートカードとして読み込んで表示すること。
  各カードは、ルート本体の値（label・基準ルートか・所要時分・4フラグ・設備・備考）と、
  適用先の方面の組み合わせ（2×2 のチェック）を持つこと。
- **REQ-4**: 駅対に接続が1つも無いとき、システムはルートカードを0枚で表示し、「未評価」であることを示すこと
  （ルートが0本の状態を「バリアフリールートが無い」と区別する。#30 REQ-4）。

### ルートの入力

- **REQ-5**: 入力者がルートカードを追加するとき、システムは適用先の方面の組み合わせの既定を**4通りすべて**
  （全方面共通）にすること。方面によって条件が変わる駅は、入力者がチェックを外し、別のカードに割り振ること。
- **REQ-6**: ルートカードは `label`（必須・100字以内。プレースホルダで「北改札経由」「地上経由」の例を示す）、
  基準ルートか、所要時分（0以上の整数または空）、4つのフラグ（屋外・改札外・係員・公式案内）、備考を
  入力できること。
- **REQ-7**: 設備は `facility_types` の7種から複数を選べること（順序・回数は入力しない。ADR-0011）。
  入力ガイドで、「同じ段差に対する代替手段（階段と階段昇降機）は同じルートに入れず、別ルートにする」ことと、
  段差の無いルートは `sameFloor` を選ぶこと（設備0件は「未入力」を表す。ADR-0012）を示すこと。
- **REQ-8**: 入力者がルートカードの複製を指示するとき、システムは同じ内容の新しいルート
  （既存の `routeId` を持たない）を作り、適用先の方面の組み合わせは空にして、入力者が割り振れるようにすること。
- **REQ-9**: 1つのルートに `stairs` と `stairLift` が同居しているとき、システムは代替手段の同居の警告を出すこと
  （保存は止めない）。
- **REQ-10**: 接続の備考は方面の組み合わせごとに保持できること。既定は全方面で同じ1欄とし、既存の値が
  組み合わせごとに異なる場合は、組み合わせごとの欄で表示すること。ルートが1本も適用されていない
  組み合わせの備考は保存しないこと。

### 保存

- **REQ-11**: 入力者が保存を指示するとき、システムは次を満たさない入力を保存せず、理由を示すこと
  （クライアントと API の両方で同じ検証を行う）:
  - 各ルートは、適用先の方面の組み合わせを1つ以上持つ
  - 同じ組み合わせの中で `label` が重複しない
  - 同じ組み合わせの中で基準ルートが2本以上ない
  - `label` は空でなく100字以内、所要時分は0以上の整数または空、設備コードは7種のいずれか
- **REQ-12**: ルートがあるのに基準ルートの無い組み合わせがあるとき、システムは「迂回度が出せない」旨の警告を出すこと
  （保存は止めない。#30 決定10のレビュー事項）。
- **REQ-13**: 保存が成功するとき、システムは駅対の**最終状態**を1トランザクションで書き込むこと。
  ルートが1本以上ある方面の組み合わせだけ接続行を持ち（端点は `normalizeTransferEndpoints()` で正規化）、
  ルートが0本になった組み合わせの接続行は削除すること。新規の接続は `source = 'manual'`、既存の接続は
  `source` を保つこと。基準ルートの付け替えでも、部分ユニーク制約に違反しないこと。
- **REQ-14**: 保存によって、どの接続からも参照されなくなったルートは、システムが削除すること
  （孤立ルートを残さない。`connection_routes` は接続の削除で cascade するが、ルートは共有されうるため
  DB では消えない）。他の接続からまだ参照されているルートは削除しないこと。

### 重複検出（#30 REQ-23 の改訂）

- **REQ-15**: 保存を指示したとき、設備が1件以上で、新規または内容が変わったルートの「設備の種類の集合＋4フラグ」が、
  候補ルート、または同じ画面の他のカードと完全に一致する場合、システムは保存前にモーダルで一致先を示し、
  「既存ルートを共有する」か「別ルートとして作る」かを選ばせること。**保存は止めない**
  （別ルートを選べば作成できる）。設備0件のルートは検出の対象外とすること（ADR-0012）。
- **REQ-16**: 入力者が「共有する」を選ぶとき、システムは、一致先が候補ルートなら新規ルートを作らず、
  そのカードの `routeId` を一致先に付け替えること。一致先が同じ画面の他のカードなら、2枚のカードを
  1枚に統合すること（適用先の方面の組み合わせは和集合。統合の結果 REQ-11 に違反する場合は保存時に拒否する）。
- **REQ-17**: 検出の範囲は S か T を端点に持つ接続のルートに限ること。中身が同じでも別の物理経路でありうる
  （例: 池袋の各線のエレベーター経由）ため、範囲外のルートは比較しない。

### 共有中のルート

- **REQ-18**: ルートが編集中の駅対の外の接続からも参照されているとき、システムはカードに「共有中」と
  共有先の駅対を示し、編集が共有先にも反映されることを示すこと。
- **REQ-19**: 入力者が「この駅対だけ切り離す」を指示するとき、システムはそのカードを、`routeId` を持たない
  同じ内容の新しいルートにすること（共有先のルートは変わらない）。
- **REQ-20**: 保存のとき、`routeId` が指定されたルートが、編集中の駅対に結ばれているか、候補ルートの範囲に
  無い場合、システムは 422 で拒否すること（無関係な接続のルートを書き換えさせない）。

### プレビュー

- **REQ-21**: ルートカードは、ベビーカーと車いすそれぞれの「必要な行為」（6値）と、バリアフリールートか
  どうかを、設備から導出して読み取り専用で表示すること（#30 REQ-13〜15）。
- **REQ-22**: ルートの設備が0件のとき、システムは必要な行為を導出せず、バリアフリールートにも数えず、
  「設備が未入力」と表示すること（ADR-0012）。
- **REQ-23**: 導出の規則は、DB にも React にも依存しない純粋関数のパッケージ（`packages/transfer-difficulty`）に置き、
  #125 の Web が同じ関数を使えること（#30 REQ-19）。

### 旧4列の撤去

- **REQ-24**: 駅の編集画面と接続の追加画面は、旧 `station_connections` の難易度4列を入力・更新しないこと。
  旧4列を更新する API（`PUT /api/station-connections/[connectionId]`）と検証スキーマ・表示定数を削除すること。
  旧4列の列そのものと Web の読み取りは #125 まで残す。
- **REQ-25**: 駅対を削除するとき、システムは `station_connections` の2行に加えて、その駅対の
  `transfer_connections` と、孤立したルートを1トランザクションで削除すること。削除の確認に、
  評価データも消えることを示すこと。

### 望ましくない動作

- **REQ-26**: 入力に「推奨乗換駅」「合理性」「おすすめ度」や、ペルソナごとの可否を直接入力する項目があってはならない
  （#30 REQ-20・21）。
- **REQ-27**: 接続の備考・ルートの備考に、出発地・目的地に依存する経路上の選好（「〇〇駅のほうが便利」）を
  書かないよう、入力欄の説明で示すこと（強制はしない。本郷三丁目の既存の備考は例外として残る）。
- **REQ-28**: 保存中に一意制約（`label` の重複）に違反した場合、システムは 409 と「同じ名前のルートがあります」を返すこと。

## 対象外

- **Web 表示**（#125）。旧4列の削除も #125 のあとの別デプロイ。
- **方面の表示文言の整備**（#130 の `isDefault`）。本Issueは `line_directions` の文言を入力の補助表示に使うだけで、
  解決規則は作らない。
- **経路探索の乗換駅選択**（#119）、**時間帯制約の構造化**（#120）、
  **設備データからのルート設備の自動導出**（#121）、**中野坂上型**（#128）。
- 複数の管理者による同時編集の競合検出（後勝ち。design.md「エラーマトリックス」）。
- 4状態の分類（未評価／バリアフリールートなし／単一／複数）と所要時分順の並べ替え（#125 で足す）。
