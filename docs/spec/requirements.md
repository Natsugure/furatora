# 要件: line_directions に isDefault を追加する（方面ラベルの解決）(Issue #130)

## 概要

- **対象**: `(路線, 走行方向)` ごとに方面の**既定の文言**を1つ決める仕組みを入れる。
  (1) `line_directions.is_default` と部分ユニークインデックス、(2) 既存行への既定の設定（データ移行）、
  (3) 方面ラベルの解決規則（純粋関数）、(4) Admin の駅対編集画面の方面の補助表示の置き換え、
  (5) Admin で既定行を保守する UI。
  Web で乗換接続の方面を表示するのは対象外（[#125](https://github.com/Natsugure/furatora/issues/125)）
- **参照**: [design.md](./design.md) / [tasks.md](./tasks.md) /
  [Issue #130](https://github.com/Natsugure/furatora/issues/130) /
  `docs/domain/station-master-model.md`「乗換難易度」節（接続の端点）
- **ブランチ**: `feat/issue130-line-direction-default`
- **信頼度**: 88%（高）。スキーマ変更は列とインデックスの追加だけで非破壊。既定行の選び方は開発者と合意済み
  （2026-09-27）。残る不確実性は、大江戸線の新しい行の代表駅（仮置き。design.md 決定5）だけ

## 背景

#30 で乗換接続の方面キーを `line_directions.id` から `direction_type`（`'inbound' | 'outbound'`）に変えた。
その結果、乗換接続の方面の**表示文言**（「池袋方面」など）を引く手段がなくなった。

- 現在の文言の引き方は `platforms.inboundDirectionId` / `outboundDirectionId` を経由するものだけ。
  `platforms` は20駅分しか登録されていない。
- `line_directions` には、同じ `(lineId, direction_type)` に同じ意味の行が複数ある
  （丸ノ内線 inbound は5行。52行・28組のうち10組が複数行）。
- #125 で「淡路町の池袋方面は途中階段」のように表示するには、`(lineId, direction_type)` から文言が1つに決まる必要がある。

Issue 本文との読み替え:

| Issue 本文 | 本書での扱い |
|---|---|
| 駅ごとの掲示文言のうち**最も一般的なもの**を既定にする | **途中の駅名を含まない、終点方向の文言**を既定にする（REQ-5）。件数が最多の丸ノ内線 inbound「東京・新宿・荻窪・方南町方面」は、新宿駅や東京駅の画面で誤りになるため。また、ホームが登録されていない路線（14路線中12路線）では件数で決まらない |
| 既存52行から選ぶ | 大江戸線は既存13行のどれも全駅に通用しないため、「内回り」「外回り」の2行を追加して既定にする（REQ-6） |

## 用語

- **組**: `(lineId, direction_type)`。1路線につき inbound・outbound の2組。
- **既定行**: 組の中で `is_default = true` の行。組ごとに0行か1行。
- **枠**: ホーム（`platforms`）の `inboundDirectionId` / `outboundDirectionId` のどちらに入っているか。
- **方面ラベル**: 駅・路線・走行方向に対して表示する文言。

## 要件（EARS記法）

### スキーマ

- **REQ-1**: システムは `line_directions` に `is_default boolean NOT NULL DEFAULT false` を持つこと。
- **REQ-2**: 同じ組に `is_default = true` の行を2行作ろうとした場合、システムは DB 制約でその書き込みを拒否すること。
- **REQ-3**: システムは既定行が0行の組を許容すること（REQ-9 の ③ にフォールバックする）。

### データ移行

- **REQ-4**: 移行を適用したとき、システムは、候補が1行しかない18組について、その行を既定にすること。
- **REQ-5**: 移行を適用したとき、システムは、候補が複数ある8組（大江戸線を除く）について、design.md 決定3 の表の行を既定にすること。
- **REQ-6**: 移行を適用したとき、システムは大江戸線に inbound「内回り」・outbound「外回り」の2行を追加し、その2行を既定にすること。
- **REQ-7**: 移行を適用したとき、既定行が既にある組がある場合、システムはその組を変更しないこと。
- **REQ-8**: 移行の対象の路線・行・駅が存在しない環境の場合、システムはその組を飛ばし、エラーにしないこと。
  同じ移行を2回適用しても結果が変わらないこと。

### 方面ラベルの解決

- **REQ-9**: 駅 S・路線 L・走行方向 D の方面ラベルを求めるとき、システムは次の順に採用すること。
  ① S の L のホームが D の枠に持つ方面の文言 → ② (L, D) の既定行の文言 → ③ D が inbound なら「上り」、outbound なら「下り」。
- **REQ-10**: ① で文言が複数ある場合（1つの走行方向に複数のホームが対応する駅。中野坂上 inbound）、
  システムは重複を除き、ホーム番号の順に「／」で連結して表示すること。
- **REQ-11**: システムは解決規則を DB と React に依存しない純粋関数として提供し、Admin と Web（#125）が同じ関数を使えること。

### Admin の駅対編集画面

- **REQ-12**: 駅対の編集画面を開いたとき、システムは適用先の 2×2 の各見出しに、REQ-9 で解決した方面ラベルを1件だけ表示すること。
  同じ意味の行を連結しないこと。

### Admin の既定行の保守

- **REQ-13**: 方面を作成・編集するとき、システムは「この路線・方面の既定の表示名にする」を選べること。
- **REQ-14**: 既定にして保存したとき、同じ組に別の既定行がある場合、システムはその既定を外してから保存すること。
  外すことと保存することは、1トランザクションで行うこと。
- **REQ-15**: 選んだ組に別の既定行がある間、システムはフォームに「現在の既定: ○○（保存すると置き換わります）」と表示すること。
- **REQ-16**: 方面を新規作成するとき、その組に既定行がまだ無い場合、システムは「既定にする」をあらかじめ選択した状態で表示すること。
- **REQ-17**: 方面の一覧を表示するとき、システムは既定行に「既定」と表示すること。
- **REQ-18**: 同じ組を既定にする書き込みが同時に行われ、一方が REQ-2 の制約に反した場合、システムは 409 を返し、再読み込みを促すこと。
- **REQ-19**: 既定行を削除したとき、システムは別の行を自動で既定にしないこと（その組は ③ にフォールバックする）。

## 対象外

- Web での乗換接続の方面の表示（#125）。Web の駅詳細の方面タブ（ホーム単位）は ① にあたり、変更しない。
- 1つの走行方向に複数のホームが対応する駅の解消（#128）。
- 物理駅の粒度への統合（#82）。現在は1駅に1路線とみなす（駅対画面の `firstLineName` と同じ）。
