# 要件: 乗り換え難易度定義の改善 (Issue #30)

## 概要

- **対象**: ドメイン定義のみ（スキーマ・Admin・Web実装は対象外。「対象外」節を参照）
- **参照**: [design.md](./design.md) / [tasks.md](./tasks.md)
- **作成日**: 2026-09-20
- **ブランチ**: `docs/issue30-transfer-difficulty-model`
- **信頼度**: 80%（中）— モデルの骨格（設備の名義尺度・ペルソナ別2本・方面粒度・無向正規化）
  は実データ16行と開発者提示の複数シナリオで検証済み。未検証なのは実装フェーズでの
  スキーマ詳細（型・制約・インデックス）であり、それは本Issueのスコープ外。

## 背景

現行の乗換難易度は `packages/database/src/schema.ts` の `station_connections` に、
ペルソナ（ベビーカー / 車いす）ごとに1軸5段階の順序尺度
（`StrollerDifficulty` / `WheelchairDifficulty`、`packages/database/src/enums.ts`）を持つ。

実装と実データ（Neon `furatora-db` main ブランチ、`station_connections` 6,950行中
難易度が入っているのは16行）を調査した結果、以下の欠陥が判明した。

1. **1軸に複数概念が混在している。** ベビーカー軸は step-free 可否・迂回度・改札外経由を、
   車いす軸は迂回度・係員対応・推奨度を、それぞれ1つの順序尺度に押し込んでいる。
   両軸の値は対応しておらず、片方から他方を導出できない。
2. **接続の属性として持ってはいけない情報を持っている。** `discouraged`
   （「可能だが非合理的で推奨できない」）や、実データの備考「隣の大手町駅のほうが便利です」
   （淡路町→新御茶ノ水）は、出発地・目的地が決まって初めて言える経路上の選好であり、
   出発地に依存しない接続の事実ではない。有楽町線↔副都心線の池袋（要町を案由に案内すると
   折返し乗車になる）が示すとおり、「どの乗換駅を使うべきか」は接続の外側の情報
   （出発地・目的地・進行方向）で決まり、接続単体の属性にはできない。
3. **軸が足りず備考に逃げている。** 御茶ノ水は `optimal` なのに備考は
   「必ず屋根のない地上の公道を通る必要があります」。屋外を表す軸が無いための代償である。
4. **粒度が足りない。** 淡路町↔小川町の備考は「丸ノ内線 池袋方面は途中階段、
   荻窪方面はエレベーターのみ」。都営浅草線・新宿線・日比谷線など方面別に条件が異なる駅が
   多数あり、駅×駅の粒度では表現できない。

いずれも `station_connections` に難易度が入っている行が16件のみ（development
ブランチは0件）であり、移行コストがほぼ無い今が定義を作り直す機会である。

## 用語

- **接続（connection）**: 隣接する2つの乗換単位（駅×方面、または駅全体）の組。無向。
- **最弱リンク（step-free via）**: バリアフリールート上で、そのペルソナが通過する際に
  最も制約が強い設備区間。
- **ペルソナ**: `stroller`（ベビーカー）/ `wheelchair`（車いす）の2種。

## 要件（EARS記法）

### 保持する事実

- **REQ-1**: 接続の評価を記録するとき、システムは値を出発地・目的地に依存しない
  「接続そのものの事実」に限定し、経路上の選好（推奨度・合理性・案内すべき乗換駅）を
  含めないこと。
- **REQ-2**: 接続に一般利用者の乗換所要時分（`normalRouteMinutes`）が入力されたとき、
  システムはそれをペルソナに依存しない値として1つだけ保持すること。
- **REQ-3**: ペルソナ（`stroller` / `wheelchair`）ごとに、接続のバリアフリールート上の
  最弱リンク（`stepFreeVia`）を、以下7値のいずれかとして保持できること:
  `same_floor` / `elevator` / `ramp` / `wheelchair_escalator` / `escalator` /
  `stair_lift` / `stairs`。
- **REQ-4**: ある接続において、ベビーカーの `stepFreeVia` と車いすの `stepFreeVia` が
  異なる値を取るとき（三田駅: 浅草線↔三田線が `stairs` / `stair_lift` など）、
  システムはこれを矛盾ではなく正当な状態として受け入れること。
- **REQ-5**: ペルソナごとに、接続の所要時分（`routeMinutes`）を個別に保持できること
  （経路自体がペルソナで分岐する場合、一般ルートの所要時分と一致しなくてよい）。
- **REQ-6**: 接続に以下3つの真偽フラグを、互いに独立して保持できること:
  屋外を通るか（`isOutdoor`）／改札外を経由するか（`requiresExitGate`）／
  係員対応が必要か（`requiresStaff`）。
- **REQ-7**: 接続の評価は、方面の組（`directionId` または全方面共通を表す `NULL`）を
  端点の一部として保持できること。
- **REQ-8**: 同一のホーム対に対して、方面を指定した行と `NULL`（全方面共通）の行が
  両方存在するとき、システムは方面が一致する行を優先し、無ければ `NULL` 行の値を使うこと
  （淡路町↔小川町: 池袋方面のみ例外行を持ち、他方面は `NULL` 行に従う）。
- **REQ-9**: 接続の評価は無向として、端点を正規化した1行で保持すること
  （`station_adjacencies` の正規化方式に合わせる）。方面が異なれば別のホーム対となり、
  別行になること（淡路町の池袋方面↔小川町と、淡路町の荻窪方面↔小川町は別行）。
- **REQ-10**: 接続に、ペルソナ非依存の備考と、ペルソナごとの備考を、それぞれ自由記述で
  保持できること。

### 導出する値（保存しない）

- **REQ-11**: あるペルソナの `stepFreeVia` が `stair_lift` のとき、システムは
  ベビーカーに対して「通れない」、車いすに対して「係員を呼ぶ必要がある」と解釈すること。
- **REQ-12**: あるペルソナの `stepFreeVia` が `escalator` または `wheelchair_escalator`
  のとき、システムはベビーカーに対して「畳んで抱える必要がある」と解釈すること。
  `wheelchair_escalator` の場合、車いすに対しては「係員を呼ぶ必要がある」と解釈し、
  `escalator` の場合は車いすに対して「通れない」と解釈すること。
- **REQ-13**: あるペルソナの `stepFreeVia` が `stairs` のとき、システムはベビーカーに
  対して「持ち上げる必要がある」、車いすに対して「駅員複数名の介助が必要」と解釈すること。
- **REQ-14**: あるペルソナの `stepFreeVia` が `same_floor` / `elevator` / `ramp` の
  いずれかのとき、システムは両ペルソナに対して「そのまま通れる」と解釈すること。
- **REQ-15**: `normalRouteMinutes` とペルソナの `routeMinutes` の両方が入力されている
  接続について、システムはその差または比を迂回度として導出できること
  （迂回度そのものを別途保存しないこと）。
- **REQ-16**: 上記 REQ-11〜14 の解釈規則は、表示層の純粋関数として実装すること
  （ADR-0003 の DTO 責務分離に合わせ、値の解釈をデータの保存責務と分離する）。

### 望ましくない動作

- **REQ-17**: 接続の評価に「推奨乗換駅」「合理性」「おすすめ度」に相当する値の入力が
  要求された場合、システムはこれを本モデルの対象外として拒否し、経路探索機能側で
  解決すべき事項として扱うこと。

## 対象外

- **スキーマ実装**（`packages/database/src/schema.ts` / `enums.ts` の変更、
  マイグレーション生成）。次の実装Issueで行う。
- **Admin入力フォーム**（`apps/admin/src/features/station-connection/`）、
  **Web表示**（`apps/web/src/components/TransferDifficultySection.tsx`）の変更。
  同じく次の実装Issueで行う。
- **経路探索における乗換駅の選択**（「どの乗換駅をおすすめするか」「折返し乗車の禁止」）。
  接続単体の属性にできないことが調査で判明したため、別の機能領域として GitHub Issue に
  起票する（design.md「先送りした将来作業」参照）。
- **時間帯制約**（早朝深夜のみ設備が閉鎖される等）、**工事中の仮設ルート**、
  **設備の質**（エレベーターの大きさ、スロープの勾配）。本モデルの軸を増やしても
  解決しない別次元であり、備考列で受け止める（design.md「決定9」参照）。
- **既存16行のデータ移行**（新モデルへの書き換え）。定義確定後の実装Issueで行う。
