# 要件: 乗換難易度 既存行のデータ移行 (Issue #123)

## 概要

- **対象**: (1) 旧 `station_connections` に入っている評価済みデータを、新モデル
  （`transfer_connections` / `connection_routes` / `transfer_routes` / `transfer_route_facilities`）へ
  書き直す**データ移行マイグレーション**、(2) その前提となる、ルートの設備を「直列の並び」から
  「種類の集合」に変える**スキーマ変更**（`transfer_route_facilities.seq` を落とす。開発者確認済み・2026-09-25）。
  読み書きするアプリコード（Repository・Admin UI・Web表示）は対象外
- **参照**: [design.md](./design.md) / [tasks.md](./tasks.md) /
  [Issue #123](https://github.com/Natsugure/furatora/issues/123) /
  スキーマは #122（PR #131）。ドメイン定義は `docs/domain/station-master-model.md`「乗換難易度」節
- **ブランチ**: `feat/issue123-transfer-difficulty-migration`
- **信頼度**: 70%（中）。移行SQLの書き方は前例（0005・0007・0010）があり不確実性は低い。
  不確実なのは**データの中身**である。旧データにはペルソナ別の難易度と備考文しかなく、新モデルが要求する
  設備の種類・所要時分・基準ルートの中身は含まれない。これらは開発者が補完する（design.md「移行データ表」）。
  中信頼度のため、SQL は `BEGIN … ROLLBACK` で先に検証してから適用する（MVP）

## 背景

#122 で新モデルのスキーマが入ったが、全表0件である。旧 `station_connections` の難易度4列
（`strollerDifficulty` / `wheelchairDifficulty` / `notesAboutStroller` / `notesAboutWheelchair`）に
入っている評価済み行を、新モデルの「接続 → 紐付け → ルート → 設備」に書き直す。
後続は #124（Admin入力）→ #125（Web表示）。

## 実データの確認結果（Neon main / development、read-only、2026-09-25）

- 難易度か備考のどちらかが入っている旧行は **17行**（Issue 本文の「16行」に、難易度 NULL・備考のみの
  御茶ノ水 丸ノ内線↔JR中央・総武線が1行加わる）。main と development で同じ17行・同じ `id`
- 旧表は有向2行で持つが、実際に値が入っているのは丸ノ内線側からの片方向が大半。
  逆向きも入っているのは後楽園↔春日（三田線・大江戸線）の2組だけで、その難易度は一致している。
  備考は片方向にしか入っていない組があるため、**逆向きの行が両方ある場合は、値のある方を採る**
- 無向の駅対にすると **15組**（Issue の「8組」は駅名で括った数）。1組につき方面2×2の接続を作るので
  **接続は60行**
- 丸ノ内線の方面は `outbound`＝池袋方面、`inbound`＝荻窪方面（`line_directions` で確認）
- 対象20駅はすべて `slug` を持つ（JR・東武・西武は非公開駅だが `slug` はある）

## 用語

- **駅対**: 旧表の（`stationId`, `connectedStationId`）を無向にした組。15組
- **接続**: 新モデルの `transfer_connections` 1行。駅対 × 方面（2×2）で1組につき4行
- **移行データ表**: design.md に置く、駅対ごとのルート・設備・フラグ・備考の確定表。
  開発者の確定を経てから SQL にする

## 要件（EARS記法）

### 移行の範囲

- **REQ-1**: 移行を実行するとき、システムは旧 `station_connections` のうち難易度4列のいずれかが
  入っている17行を、無向の15駅対として新モデルへ書き直すこと。逆向きの行が両方ある駅対は、
  値のある方を採ること。
- **REQ-2**: 旧行に無い駅対（三田・西日暮里・霞ケ関ほか、Issue #123「移行の対象外だが、入力が必要な接続」）
  について、システムは新表に行を作らないこと（「行が無い＝未評価」を保つ）。

### 接続

- **REQ-3**: 各駅対について、システムは方面の組み合わせ（`inbound`/`outbound` × `inbound`/`outbound`）
  4行の接続を作ること。端点は `transfer_connection_endpoints_ordered` の CHECK と同じ順序
  （`(stationId, direction_type)` の昇順）で格納すること。
- **REQ-4**: 接続の `source` は、旧行の `source` を引き継ぐこと（`ekidata_group` / `manual`）。

### ルートと共有

- **REQ-5**: 方面によって物理経路が変わらない接続どうしは、ルート行を複製せず、
  同一の `transfer_routes` 行を `connection_routes` で共有すること。
- **REQ-6**: 淡路町↔小川町では、丸ノ内線側の方面ごとに異なるルートを共有すること
  （池袋方面側の2接続が階段・エスカレーターを含むルートを、荻窪方面側の2接続がエレベーターのみの
  ルートを、それぞれ共有する）。設備行はルートの本数分だけ作り、複製しないこと。
- **REQ-7**: 各接続について、システムは基準ルートをちょうど1本結ぶこと
  （`connection_routes.is_baseline = true`）。
- **REQ-8**: 各紐付けの `label` は、経路が識別できる名前（「北改札経由」「地上経由」の類）とすること。

### 設備・フラグ

- **REQ-9**: 各ルートについて、システムは通る設備を**種類の集合**として保持すること
  （順序・回数は持たない。同じ種類は1行）。集合は「そのルートは、これらをすべて通る」を意味するため、
  同じ段差に対する代替手段（階段と車いす対応エスカレーター等）は同一ルートに入れず、別ルートとすること。
- **REQ-10**: ルートの4フラグ（`isOutdoor` / `requiresExitGate` / `requiresStaff` / `isOfficiallyGuided`）と
  `minutes` は、移行データ表で確定した値を入れること。所要時分が確認できないルートは `NULL` を許容する。

### 備考

- **REQ-11**: 淡路町↔新御茶ノ水の備考「隣の大手町駅のほうが便利です」は、出発地に依存する経路上の
  選好であるため、システムは移行しないこと（#30 決定1・決定9）。
- **REQ-12**: ペルソナ別の備考は、システムがルートの `notes` か設備の種類に振り分けること。
  設備・フラグで表現される内容（「必ず屋根のない地上の公道を通る」= `isOutdoor`、
  「改札係員に申し出る」= `requiresStaff`）は、備考に重複して残さないこと。
- **REQ-13**: 本郷三丁目の備考「隣の後楽園・春日駅の乗り換えであれば屋内で完結しますが…一長一短です」は、
  開発者の判断により削除せず、接続の `notes` に残すこと。ベビーカー側と車いす側で異なる語
  （「歩行距離」「移動距離」）は「移動距離」に統一する。

### 設備の集合化（スキーマ変更）

- **REQ-19**: `transfer_route_facilities` は `seq` を持たず、`(routeId, typeCode)` の一意制約を持つこと。
  同じルートに同じ種類の設備を2行入れようとした場合、システムはDB制約でこれを拒否すること。
- **REQ-20**: このスキーマ変更は新しいマイグレーション（0011）で行い、適用済みの 0009 を書き換えないこと。
  対象表が全環境で0行であり `seq` を読み書きするコードが無いことを、適用前に確認すること
  （CLAUDE.md の破壊的マイグレーションの二段階規則に当たらないことの確認）。
- **REQ-21**: 設備の並びと4フラグの一致による重複ルートの検出（#124）は、設備の種類の集合の一致として
  判定できること。並びの違いだけで別ルートとして扱ってはならない。

- **REQ-22**: 設備が0件のルートについて、システムは「設備未入力」として扱うこと。
  必要な行為を導出せず、バリアフリールートにも数えず、設備の情報が未入力であることを示す（#125）。
  段差の無いルートは `sameFloor` を明示して入力する（#124）。本Issueは移行で設備0件のルートを作るため、
  この規則を `docs/domain/` に書くこと（決定5）。

### 適用・安全性

- **REQ-14**: 移行マイグレーションは Vercel のビルドで自動適用されるため、対象20駅のいずれかの
  `slug` が存在しない環境（駅データが無い新規環境）、または使用する設備の種類
  （`elevator` / `ramp` / `stairLift` / `wheelchairEscalator`）が `facility_types` に無い環境
  （マスタ未投入の環境）では、システムはデータを投入せず、ビルドを失敗させずに終了すること。
- **REQ-15**: 対象の接続が既に1行でも存在する場合、システムはデータを投入せず終了すること
  （二重投入を防ぐ）。
- **REQ-16**: 移行マイグレーションは、1つの文として原子的に適用されること。
  途中で失敗した場合、新表に中途半端な行が残らないこと。
- **REQ-17**: 本変更は旧 `station_connections` の行・列を変更・削除しないこと
  （旧4列は #125 まで現行の Admin・Web が読む。落とすのは #125 のあとの別デプロイ）。
- **REQ-18**: `pnpm run build` は DB に書き込まないこと。データの投入はマイグレーションだけが行う。

## エッジケース

| ケース | 扱い |
|---|---|
| 逆向きの旧行で備考が片方だけ（後楽園↔春日 三田線） | 値のある方を採る（REQ-1） |
| 難易度 NULL・備考のみの旧行（御茶ノ水 丸ノ内↔JR中央・総武） | 移行する。備考の事実（屋外・改札外）はフラグに移す |
| ベビーカーと車いすで備考の文言が微妙に異なる（本郷三丁目） | 語を統一して1つにする（REQ-13） |
| 設備の種類が旧データから確定できない | 開発者が補完する。確認できない場合の扱いは design.md「未決事項」 |
| 同種の設備が複数か所ある（階段が2か所等） | 1行に集約される（回数は持たない。必要になったら `count` 列を足す） |
| 環境ごとに `id` が違う | 駅は `slug` で引く（REQ-14） |
| 移行後に旧行が Admin で編集された | 旧表は #125 まで現行の読み書き対象。マージ直前に旧17行が変わっていないか再確認する（tasks.md） |
