# 要件: 乗り換え難易度定義の改善 (Issue #30)

## 概要

- **対象**: ドメイン定義のみ（スキーマ・Admin・Web実装は対象外。「対象外」節を参照）
- **参照**: [design.md](./design.md) / [tasks.md](./tasks.md)
- **作成日**: 2026-09-20 / **改訂**: 2026-09-21
- **ブランチ**: `docs/issue30-transfer-difficulty-model`
- **信頼度**: 85%（高）— 実在する8シチュエーション（開発者提示）と実データ16行で机上検証済み。
  未検証なのは実装フェーズでのスキーマ詳細（型・インデックス・DTOの形）であり、本Issueのスコープ外。

### 改訂の要旨（2026-09-21）

初版は「接続1行にペルソナごとの列を持つ」モデルだった。実在8シチュエーションで検証した結果、
3つが表現できないことが判明したため、**接続とペルソナの間に「ルート」を挟むモデルに作り直した**。

| 表現できなかったもの | 初版の限界 |
|---|---|
| 西日暮里（同一ペルソナに2つの選択肢） | 1ペルソナ1組の値しか持てず、片方が備考に落ちる |
| 高田馬場と御茶ノ水の区別 | 一般ルートに所要時分しか持てず、「自分だけ屋外」と「全員屋外」が同じ行になる |
| 霞ケ関（ベビーカーにバリアフリールートが無い） | 「ルートが無い」を表す値が無く、未評価の `NULL` と区別できない |

## 背景

現行の乗換難易度は `packages/database/src/schema.ts` の `station_connections` に、
ペルソナ（ベビーカー / 車いす）ごとに1軸5段階の順序尺度
（`StrollerDifficulty` / `WheelchairDifficulty`、`packages/database/src/enums.ts`）を持つ。

実装と実データ（Neon `furatora-db` main ブランチ、`station_connections` 6,950行中
難易度が入っているのは16行）を調査した結果、以下の欠陥が判明した。

1. **1軸に複数概念が混在している。** ベビーカー軸は step-free 可否・迂回度・改札外経由を、
   車いす軸は迂回度・係員対応・推奨度を、それぞれ1つの順序尺度に押し込んでいる。
   両軸の値は対応しておらず、片方から他方を導出できない。
2. **接続の属性として持ってはいけない情報を持っている。** `discouraged`
   （「可能だが非合理的で推奨できない」）や、実データの備考「隣の大手町駅のほうが便利です」
   （淡路町→新御茶ノ水）は、出発地・目的地が決まって初めて言える経路上の選好であり、
   出発地に依存しない接続の事実ではない。
3. **軸が足りず備考に逃げている。** 御茶ノ水は `optimal` なのに備考は
   「必ず屋根のない地上の公道を通る必要があります」。屋外を表す軸が無いための代償である。
4. **粒度が足りない。** 淡路町↔小川町の備考は「丸ノ内線 池袋方面は途中階段、
   荻窪方面はエレベーターのみ」。方面別に条件が異なる駅が多数ある。
5. **経路が1本である前提を置いている。** 西日暮里のように、同じ接続に対して
   「階段昇降機＋駅員介助（屋内・短い）」と「改札外エレベーター（屋外・遠回り・介助不要）」が
   併存する駅がある。どちらを選ぶかは利用者の事情で逆転するため、入力者が決めてはならない。

いずれも `station_connections` に難易度が入っている行が16件のみ（development
ブランチは0件）であり、移行コストがほぼ無い今が定義を作り直す機会である。

## 用語

- **接続（connection）**: 隣接する2つの乗換単位（駅×方面）の組。無向。
- **ルート（route）**: 1つの接続を渡る**1本の物理経路**。1つの接続は0本以上のルートを持つ。
- **基準ルート（baseline route）**: 一般利用者が案内される経路。迂回度の分母になる。
- **設備（facility）**: ルート上を通過する際に使う昇降手段。エレベーター、階段、階段昇降機など。
- **ペルソナ**: `stroller`（ベビーカー）/ `wheelchair`（車いす）の2種。
- **必要な行為（requirement）**: あるペルソナがあるルートを通るために必要になること。6値（REQ-12）。
- **バリアフリールート**: 必要な行為が「そのまま通れる」または「係員を呼ぶ」であるルート（REQ-14）。

## 要件（EARS記法）

### 接続が保持する事実

- **REQ-1**: 接続の評価を記録するとき、システムは値を出発地・目的地に依存しない
  「接続そのものの事実」に限定し、経路上の選好（推奨度・合理性・案内すべき乗換駅）を
  含めないこと。
- **REQ-2**: 接続を保持するとき、システムは評価を無向として、端点を正規化した1行で保持すること
  （`station_adjacencies` の正規化方式に合わせる）。端点は `(駅, 方面)` の組とし、
  方面には「全方面共通」を表す `NULL` を許容すること。方面が異なれば別の端点対として
  別行になること（淡路町の池袋方面↔小川町と、淡路町の荻窪方面↔小川町は別行）。
- **REQ-3**: 同一の駅対に対して複数の行が該当するとき、システムは次の優先順位で1行に解決すること。
  1. 両端点の方面が一致する行
  2. 片側の方面が一致し、もう片側が `NULL` である行
  3. 両端点が `NULL`（全方面共通）の行
  2. に該当する行が両側分（`(A指定, B=NULL)` と `(A=NULL, B指定)`）同時に存在する場合は、
  正規化順で先にくる端点側の一致を採ること。この同時存在は運用上の誤りであるため、
  Admin はこの状態を警告すること。
- **REQ-4**: 接続に該当する行が1件も無いとき、システムはこれを「未評価」として扱い、
  「バリアフリールートが無い」（REQ-15）と区別すること。

### ルートが保持する事実

- **REQ-5**: 1つの接続に対して、システムは0本以上のルートを保持できること。
  1本のルートは1つの物理経路を表すこと。
- **REQ-6**: ルートを保持するとき、システムは経路の識別名（`label`）を必須とし、
  同一接続内で重複を許さないこと（「北改札経由」「地上経由」など）。
- **REQ-7**: ルートを保持するとき、システムは「一般利用者が案内される基準ルートか」
  （`isBaseline`）を保持し、1つの接続につき基準ルートを**高々1本**に制限すること。
- **REQ-8**: ルートを保持するとき、システムは所要時分（`minutes`）と、
  互いに独立した4つの真偽値を保持できること:
  屋外を通るか（`isOutdoor`）／改札外を経由するか（`requiresExitGate`）／
  係員対応が必要か（`requiresStaff`）／事業者が公式に案内しているか（`isOfficiallyGuided`）。
- **REQ-9**: ルートを保持するとき、システムはそのルートが**直列に**通過する設備の並びを
  保持できること。同じ段差に対する代替手段（階段と階段昇降機）は直列ではないため、
  同一ルートの設備として並べず、別のルートとして保持すること。
- **REQ-10**: 設備は以下7値のいずれかとして保持できること:
  `same_floor` / `elevator` / `ramp` / `wheelchair_escalator` / `escalator` /
  `stair_lift` / `stairs`。
- **REQ-11**: システムは接続単位の備考とルート単位の備考を、それぞれ自由記述で保持できること。
- **REQ-12**: システムはペルソナごとの可否・必要な行為・所要時分を**保持しない**こと
  （すべて設備から導出する。REQ-13〜14）。

### 導出する値（保存しない）

- **REQ-13**: 設備とペルソナの組が与えられたとき、システムは「必要な行為」を
  以下のとおり解釈すること。

  | 設備 | ベビーカー | 車いす |
  |---|---|---|
  | `same_floor` / `elevator` / `ramp` | そのまま通れる | そのまま通れる |
  | `wheelchair_escalator` | 畳んで抱える | 係員を呼ぶ |
  | `escalator` | 畳んで抱える | 通れない |
  | `stair_lift` | 通れない | 係員を呼ぶ |
  | `stairs` | 持ち上げる | 駅員複数名の介助 |

- **REQ-14**: ルートとペルソナの組が与えられたとき、システムはそのルート上の設備すべてに
  REQ-13 を適用し、**そのペルソナにとって最も重い行為**をルートの必要な行為とすること。
  「重さ」の順序はペルソナごとに異なり、以下のとおりとすること。
  - ベビーカー: そのまま通れる ＜ 畳んで抱える ＜ 持ち上げる ＜ 通れない
  - 車いす: そのまま通れる ＜ 係員を呼ぶ ＜ 駅員複数名の介助 ＜ 通れない
- **REQ-15**: 必要な行為が「そのまま通れる」または「係員を呼ぶ」であるルートを、
  システムはそのペルソナにとっての**バリアフリールート**として扱うこと。
  「畳んで抱える」「持ち上げる」「駅員複数名の介助」は通行可能だがバリアフリールートではなく、
  「通れない」は通行不可として扱うこと。
- **REQ-16**: 接続とペルソナの組が与えられたとき、システムは表示を以下の4状態に分類すること。

  | 状態 | 条件 | 表示 |
  |---|---|---|
  | 未評価 | ルートが0本 | 情報が無いことを示す |
  | バリアフリールートなし | バリアフリールートが0本 | その旨と、通行可能なルートのうち最も軽い行為を示す |
  | 単一 | バリアフリールートが1本 | そのルートを示す |
  | 複数 | バリアフリールートが2本以上 | すべて並記し、値が異なる項目を強調する |

- **REQ-17**: 複数のバリアフリールートを並べるとき、システムは所要時分の昇順でのみ
  並べ替えること。必要な行為で並べ替えないこと（「畳んで抱える」と「係員を呼ぶ」の
  どちらが軽いかは利用者によって逆転するため）。所要時分が未入力のルートは末尾に置くこと。
- **REQ-18**: 基準ルートの所要時分と、そのペルソナのバリアフリールートのうち最短の
  所要時分の両方が入力されているとき、システムはその差または比を迂回度として導出できること
  （迂回度そのものを別途保存しないこと）。
- **REQ-19**: REQ-13〜18 の解釈規則は、表示層の純粋関数として実装すること
  （ADR-0003 の DTO 責務分離に合わせ、値の解釈をデータの保存責務と分離する）。
  DTO はルートと設備をそのまま運び、ペルソナによる絞り込みを行わないこと。

### 望ましくない動作

- **REQ-20**: 接続またはルートの評価に「推奨乗換駅」「合理性」「おすすめ度」に相当する値の
  入力が要求された場合、システムはこれを本モデルの対象外として拒否し、経路探索機能側で
  解決すべき事項として扱うこと。
- **REQ-21**: ペルソナごとの可否（「ベビーカーは通れる」等）を直接入力させる要求があった場合、
  システムはこれを拒否し、設備の記録として受け取ること（解釈をデータに焼き付けないため）。
- **REQ-22**: 1つの接続に2本目の基準ルート、または同一接続内で重複する `label` の
  ルートを作成しようとした場合、システムはこれを拒否すること。
- **REQ-23**: 設備の並びと4つの真偽値が既存ルートと完全に一致するルートを作成しようとした場合、
  Admin は保存を中断し、既存のルートを示すこと（同一経路の二重登録を防ぐため）。

## 対象外

- **スキーマ実装**（`packages/database/src/schema.ts` / `enums.ts` の変更、
  マイグレーション生成）。[Issue #122](https://github.com/Natsugure/furatora/issues/122) で行う。
- **Admin入力フォーム**（`apps/admin/src/features/station-connection/`）、
  **Web表示**（`apps/web/src/components/TransferDifficultySection.tsx`）の変更。
  [#124](https://github.com/Natsugure/furatora/issues/124) /
  [#125](https://github.com/Natsugure/furatora/issues/125) で行う。
- **経路探索における乗換駅の選択**（「どの乗換駅をおすすめするか」「折返し乗車の禁止」）。
  接続単体の属性にできないことが調査で判明したため、別の機能領域として扱う
  （[#119](https://github.com/Natsugure/furatora/issues/119)）。
- **時間帯制約**（早朝深夜のみ設備が閉鎖される、係員が不在になる等）、**工事中の仮設ルート**、
  **設備の質**（エレベーターの大きさ、スロープの勾配）。本モデルの軸を増やしても
  解決しない別次元であり、備考列で受け止める（[#120](https://github.com/Natsugure/furatora/issues/120)）。
- **改札外ルートの運賃上の扱い**（追加運賃の有無、IC の出場入場処理）。
  `requiresStaff` と備考で受け止め、構造化は実データの蓄積後に判断する（design.md 決定7）。
- **既存16行のデータ移行**（新モデルへの書き換え）。
  [#123](https://github.com/Natsugure/furatora/issues/123) で行う。
