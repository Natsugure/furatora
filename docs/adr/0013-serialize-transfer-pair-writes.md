# ADR-0013: 駅対の乗換難易度の書き込みを、接続一覧の行ロックで1本ずつにする

- **ステータス**: Accepted
- **日付**: 2026-09-27
- **決定者**: @Natsugure
- **関連**: [ADR-0005](./0005-write-atomicity-driver.md),
  [`docs/domain/station-master-model.md`](../domain/station-master-model.md)「Admin の書き込み規約」,
  GitHub Issue #124 / PR #133

---

## コンテキストと課題

Admin の乗換難易度の保存（`transferConnectionRepository.savePair`）は、駅対の**最終状態**を1回で受け取り、
1トランザクションで次を行う（[ADR-0005](./0005-write-atomicity-driver.md)）。

1. 既存の接続（`transfer_connections`）を読む
2. 無い組み合わせの接続を INSERT する
3. 紐付け（`connection_routes`）を全部消してから入れ直す

分離レベルは READ COMMITTED で、ロックを取っていなかった。そのため同じ駅対への保存が並行すると、
どちらも「既存の接続は無い」と読んで同じ端点を INSERT し、後の方が `unique_transfer_connection` 違反で
**中身の無い 500** になった（PR #133 のレビューで指摘し、development ブランチで再現）。
評価済みの駅対でも、紐付けを消して入れ直す間に競合し、紐付けが二重になりうる。

同様に `stationConnectionRepository.deletePair`（接続一覧と評価データの削除）が保存と並行すると、
削除の直後に評価データだけが書き戻され、接続一覧の無い評価データが残りうる。

## 決定

駅対 {S, T} の乗換難易度を書く・消すトランザクションは、**最初に接続一覧（`station_connections`）の
S→T・T→S の2行を `SELECT … FOR UPDATE` でロックする**（`external/transferPairSql.ts` の `lockStationPair`）。

- 同じ駅対への保存・削除は1本ずつ進む。後から来た書き込みは、先の書き込みのコミットを待ってから読み直す。
- 2行は **id の順にロックする**。S→T の画面と T→S の画面から同時に保存したとき、ロックの順序が
  食い違ってデッドロックするのを避けるため。
- 後から保存した方が、先の保存を上書きする（最終状態の全置換なので、後勝ち）。

## 却下した選択肢

### 一意制約違反を 409 に変えるだけ

`unique_transfer_connection` の違反を「他の保存と競合しました」として返す案。変更は最小だが、
未評価の駅対の INSERT 競合しか扱えない。評価済みの駅対で紐付けの入れ直しが競合する場合や、
削除との競合は、エラーにもならずに不整合が残りうる。

### 楽観ロック（版の比較）

画面が読み込んだ時点の版を送り、DB 側で版が変わっていれば 409 を返す案。後勝ちの上書き（lost update）まで
防げるが、駅対単位の版を持つ列が無く、スキーマ変更が要る。Admin は開発者1人が使う前提で、
同じ駅対を複数人が同時に編集する運用が無い。現時点では過剰。

### アドバイザリロック（`pg_advisory_xact_lock`）

駅対の id から作ったキーでロックする案。行が無くてもロックできるが、キーの作り方（正規化順・ハッシュの衝突）を
別に決める必要がある。駅対は必ず `station_connections` の行を持つ（無ければ保存できない）ので、
既存の行をロックすれば足りる。

## 影響

- 同じ駅対への並行した保存は、500 にならず、どちらも成功する（後勝ち）。
  development ブランチで、同じ側から2本・S→T と T→S から1本ずつの並行保存が、どちらも 200 になり、
  接続・紐付け・ルートが1組だけ残ることを確認した。
- **駅対の乗換難易度を書く・消す処理を足すときは、同じトランザクションの最初に `lockStationPair` を呼ぶこと。**
- 後勝ちの上書きは残る。Admin を複数人で同時に使う運用になったら、楽観ロックを再検討する。
- ロックの範囲は駅対に閉じる。共有ルート（別の駅対の接続からも参照されるルート）の本体の更新は、
  別の駅対の保存とは直列にならない。

## レビュー

Admin を複数人で使う運用になったとき、または共有ルートの更新競合が実際に問題になったときに再評価する。
