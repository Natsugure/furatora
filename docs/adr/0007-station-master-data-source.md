# ADR-0007: 駅・路線マスタを ODPT 同期から駅データ.jp の初回シードに移行し、以後は手動で維持する

- **ステータス**: Proposed
- **日付**: 2026-08-27
- **決定者**: @Natsugure
- **関連**: [ADR-0001](./0001-layer-structure.md), GitHub Issue #56

---

## コンテキストと課題

駅・路線マスタの同期元は現在 ODPT だが、対応路線が少なすぎて全国を扱えない。
この制約は ODPT 側の提供範囲に起因するものであり、furatora 側の実装では解消できない。

Issue #56 は、乗換案内（経路探索）の実装を控えていることから
**マスタソースと経路探索APIをセットで選定する**前提で立てられた。
実際に比較すると、その前提は規約によって崩れた。

- **駅すぱあと API**: 駅・路線マスタの保存は認められる。
  一方で第27条1項(10)① が、乗換案内サービスの開発そのものを事前承諾なしに禁じている
- **NAVITIME API**: 競合サービスに関する条項は存在しない。
  一方で第5条5項が、緯度経度を名指しでキャッシュ・保存禁止としている

**マスタソースには「保存できること」が要る。経路探索には「契約が事業自体を禁じないこと」が要る。**
この2つを同時に満たすベンダが候補に存在しなかった。両者は同じ決定では扱えない。

### 経路探索を本ADRの対象から外す理由

経路探索は未着手である。ベンダを選定したとしても、
無料枠の実利用量・突合の誤マッチ率・規約変更といった再評価の条件は、
いずれも実装してみなければ判明しない。

すなわち実装前のベンダ選定は「覆すときに明示的な意思決定を必要とする事項」ではなく、
実装フェーズで自動的に再評価される予定作業である。
[ADR運用ルール](../../.claude/rules/adr.md) の判定基準に従い、これは ADR ではなく Issue に置く。

加えて、NAVITIME を採用すると「レスポンスをキャッシュしない」「経路上の駅を
リクエストのたびに自前DBと突合する」というアーキテクチャ上の制約が生じる。
未実装の機能のためにこの制約を先に背負う理由がない。

## 決定

1. **駅・路線マスタは 駅データ.jp（ekidata.jp）の CSV に移行する。**
   **会員版（有償）を用いる。** 無料版は駅名カナ・路線色・新幹線駅を欠き、
   それぞれが機能欠落に直結する（実測は「却下した選択肢」参照）。
   **駅名ローマ字は理由に含めない**（同節および「影響」参照）

   **取り込みは初回の一括投入限りとし、継続的な同期は行わない。**
   以後の駅・路線マスタは Admin での手動編集で維持する
   （根拠は「却下した選択肢」の「ekidata を定期的に再取込して同期する」を参照）

2. **経路探索の方式・ベンダは本ADRでは決定しない。** Issue #56 で継続検討し、
   実装フェーズで別ADRとして起票する。

3. **ODPT のマスタ同期は廃止するが、ODPT ID は動的データへの参照キーとして保持する。**
   - `stations.odptStationId` / `lines.odptRailwayId` / `operators.odptOperatorId` は残す。
     ただし**一意制約からは外し、同期されない対応スナップショットとして扱う**
   - ODPT 同期機構に属する部品は破棄する。具体的には
     `stationConnections` の ODPT ID 列と `odptMetadata` テーブルである
   - **`ekidataStationCd` / `ekidataLineCd` / `ekidataCompanyCd` も同じ性格の列である。**
     継続同期しない以上、これらは ekidata との対応スナップショットであり、
     **由来の記録**と**限定的な部分取込**の余地のために残す
   - **`ekidata*Cd` は nullable のままとし、notNull 化しない。**
     手動で追加された駅・路線は ekidata のコードを持ち得ず、
     notNull は手動運用そのものを禁じる制約になる。
     「2行が同じ ekidata 駅を主張しない」という保証は `unique` が担っており、
     `unique` は NULL を重複と見なさないため手動追加行と共存する

4. **移行機構は使い捨てとする。** CSV の取込・突合を行う Admin の機構
   （`master-import` / `master-migration`）は初回投入のためだけに存在し、
   **投入完了後に削除する。**
   - 一度きりの操作のために恒久的な画面を残すと、再実行によって
     手動で確定した表記が黙って上書きされる経路が常設される
   - 削除の時期と手順は実装計画であり、[tasks.md](../spec/tasks.md) の Phase 7 に置く

## 却下した選択肢

### ekidata の無料版CSVで運用する

費用がかからない。ekidata を選ぶ以上、まず検討すべき既定案である。

**却下した。無料版の欠落が機能欠落に直結するためである。**
2026年8月版の配布ファイルを実測した結果は以下のとおり。

| 項目 | 無料版の実測 | 却下理由に数えるか |
|---|---|---|
| `station_name_k`（駅名カナ） | **10,962件すべて空** | **数える** |
| `line_color_c`（路線色） | 624路線中 **48路線のみ**。JR・大手私鉄・都営は全滅 | **数える** |
| 新幹線の駅 | **12路線すべて0駅**。`line` と `join` には存在するのに `station` だけ欠落 | **数える** |
| `station_name_r`（駅名ローマ字） | **10,962件すべて空** | **数えない**（後述） |

**カナの欠落が決定的である。** 駅名検索（`stations.name_kana` への部分一致）を
全国駅に対して無効化するだけでなく、**`stations.slug` の導出元でもある**ため
URL 設計まで巻き込む。路線色の欠落は路線を識別するUIを、
新幹線駅の欠落は「東京駅で新幹線が出てこない乗り換え案内」を意味する。

**この3つは自前では埋められない。** 駅名の読みは難読固有名詞を多く含み、
漢字から機械生成しても表示に使える品質にならない。

**ローマ字の欠落は却下理由に数えない。** 会員版は `station_name_r` を供給するが、
**furatora はこの列を採用しない。** 会員版の実測で、現役10,625行の **97.9%** が
`station_name_k` から機械再現でき、この列は固有の情報を持たないためである。
したがって無料版でローマ字が空であることは、それ自体では損失にならない
（`stations.slug` はカナから導出する。規則は
[design.md](../spec/design.md) の範囲）。

**会員版を買う理由は、カナ・路線色・新幹線駅の3点で足りる。**

会員版は6か月4,000円である。[利用規約](https://ekidata.jp/agreement.php)は
無料版と共通で、第5条注釈が有償システムへの組み込みを明示的に許可している。
代替手段（別ソースの併用・形態素解析による読み生成）の工数と釣り合わない。

### ODPT の継続（他ソースとのハイブリッド）

対応路線が少なすぎるという当初の問題がそのまま残る。
補完のために別ソースを併用すれば、**2つの同期経路を恒久的に保守する**ことになる。
ekidata が全国625路線・10,962駅を単独で賄える以上、その複雑さに見合わない。

### ekidata を定期的に再取込して同期する

Phase 3 のリハーサル（2026-09-04）を通じて却下した。却下の理由は2つある。

1. **旅客案内の観点では ekidata の精度が期待に届かない。**
   路線は運行系統ではなく事業者の線路名の粒度で与えられる。
   実際、突合済みの路線名を ekidata の値で上書きすると
   `常磐線快速` → `JR常磐線(上野～取手)`、`高崎線` → `JR高崎線` となり、
   利用者に示す名前としては現行の方が適切である。
   駅名ローマ字を採らない判断（「影響」参照）と同じ性質の問題である

2. **新駅・廃駅・開業・廃線は年間で数えられる件数しかない。**
   その頻度に対して、CSV の取得・突合・差分確認の工数は見合わない。
   同じ変更は Admin での手動編集の方が安く、かつドメインに合った値を入れられる

**再取込を続けた場合の具体的な害は、手動で確定した表記が上書きされることである。**
取込の SET 句は、人が直した値と ekidata の値を区別できない。

なお初回の一括投入それ自体は、10,148駅・543路線を手で入力する代替が成立しないため
依然として必要である。**却下したのは継続同期であって、初回投入ではない。**

### 駅すぱあと API をマスタソースにする

**機能面では最有力だった。**

- 駅情報API・運行路線情報APIとも全件取得が可能（100件/回 + `offset` ページング）
- 駅に緯度経度が付き、路線に**路線色（RGB）**が付く。後者は ekidata が欠くものである
- 課金は HTTP ステータス 200 のリクエストのみ。上限超過しても停止せず超過料で継続
- 全国約11,000駅の初期同期は約110リクエスト。5000リクエストパックの3%に満たない
- 保存を禁じているのは鉄道時刻情報**だけ**である（第27条1項(8)）。駅・路線マスタは保存できる

**それでも採れない。第27条1項(10)① が furatora そのものを禁じているためである。**

> (10) 当社から事前の書面による承諾を受けることなく、当社の事業と競合するサービス（次のいずれかに該当するサービスを指します。）を開発、提供又は販売する行為
> ①経路検索・乗換案内サービス ②公共交通データ提供サービス ③公共交通データを取り扱うAIモデルや分析ツール ④公共交通データを取り扱うコンサルティング ⑤その他①②③④に関連するサービス

同項 (9) が「出力データを使用して」競合サービスを開発する行為を禁じるのに対し、
**(10) にはその限定がない。** 契約者である間、事前の書面承諾なしに
乗換案内サービスを開発・提供・販売すること自体を禁じる建て付けである。
furatora は定義上「乗り換え案内を提供するWebアプリ」であり、①に文言上そのまま該当する。
⑤「その他①②③④に関連するサービス」で外縁も広く取られている。

**マスタデータのみを利用する場合でも契約者になる以上、(10) の適用を免れない。**
Amazon の従量課金パックに添付される規約リンクを辿ると、
このスタンダードプラン規約が表示される。個人購入でも同じ条項が適用される。

(10) は「事前の書面による承諾」で解除できる。
しかし**同社は法人による直接契約を前提とした問い合わせのみを受け付けており、
個人開発者が承諾を求める窓口が実質的に存在しない。**
したがって「承諾を取得できれば採用する」という条件付きの選択肢が成立しない。

### NAVITIME API をマスタソースにする

規約 第5条5項により不可。

> 第5項 お客様は、本サービスを通じて当社から提供を受けたデータ（本サービスの利用により出力された緯度経度情報も含みますがこれに限られません。）をキャッシュ等に保存してはならないものとします。

`transport_node` 等で駅を取得できたとしても、緯度経度を名指しで保存禁止しているため
自前DBに置けない。マスタソースは「保存できること」が前提であり、この時点で候補から外れる。

なお経路探索の用途では、保存禁止と設計上両立しうる。
NAVITIME は Issue #56 に経路探索の候補として残る。

### ODPT ID を完全に破棄する（YAGNI）

保持コストは nullable な列3つにすぎないが、それは「残す」根拠にはならない。
破棄しても既存行が消えるわけではなく、ODPT API を引ける間は同じ突合をやり直せば
対応表を再生成できる。その意味でこの破棄は一方通行ではない。

**却下したのは、経路探索の方式を決定2で保留したためである。**

ekidata は時刻表・運行情報・列車ロケーションを原理的に持たない。
ODPT はこれらを無償かつ合法に取得できる唯一の候補であり、
経路探索の方式を決める際の主要な材料になる。
方式を保留すると決めた以上、**その材料への唯一の結合キーを今の判断で潰すことはできない。**
保留の意味が損なわれる。

加えて、JR東日本の東京近郊路線のようにコンテスト期間中のみ提供される範囲は、
提供の窓が閉じた後は再取得できない。この範囲に限っては破棄が一方通行になる。

## 影響

- **`stations` / `lines` の一意制約は ekidata のコードを鍵とするものに置き換わる。**
  現行の `uniqueStationPerOperator` は `odptStationId` を鍵にしており、
  同列が nullable であるため ODPT 由来でない駅は制約をすり抜けている。
  移行はこの潜在的な不整合を解消する機会でもある
- ODPT ID 列は一意制約から外れる。**なぜ一意でなくなったかをスキーマのコメントに残す。**
  残さなければ、次にスキーマへ触れる者が制約の欠落をバグと判断する
- **移行は in-place で行う。** `platforms` / `facilities` 等が `stations.id` を参照しており、
  既存行を作り直すと設備データが孤児になる。
  既存の ODPT 由来行を ekidata 駅に突合して UPDATE し、残余を INSERT する
- `stationConnections` の ODPT ID 列は、DB未登録の接続先を後から解決するための暫定機構だった。
  全国の駅が揃えば「未登録の接続先」という状況自体が消えるため不要になる
- **会員版の `station_name_r`（駅名ローマ字）は採用しない。**
  現役10,625行の97.9%が `station_name_k` から機械再現でき固有の情報を持たない上、
  正式な英語表記に必要なハイフンと大文字（`Kita-senju` 等）は
  カナにもローマ字列にも無く、原理的に導出できない。
  英語名は事業者公式のもの（ODPT 由来）のみを入れ、機械生成しない。
  結果として、全国展開分の英語名は欠落したまま運用する
- **駅ナンバリングは会員版にも無い。** 駅すぱあとを採れなかった代償である。
  ただし現行DBが持つ146件は ODPT 由来の手入力であり、突合して UPDATE すれば残る。
  `odptStationId` を保持する限り、ODPT から再取得する道も残る
- ekidata は路線×駅粒度を持つ。`facilityConnections` が接続先を駅単位でしか持てない問題を
  解消できる可能性がある。粒度の設計は `docs/spec/` の範囲であり本ADRでは扱わない
- **ekidata は駅間所要時間を持たず、直通運転も表現できない。**
  自前経路探索を選ぶ場合の主要な障害であり、本ADRはこれを解決しない。
  `join` データは取り込み、選択肢としては残す
- **ekidata の出典表示は義務ではない**（第4条「弊社のデータであることを明記する必要はない」）。
  任意表記は歓迎されている。ODPT 由来の ID を保持し続ける場合に
  ODPT 側の出典表示義務が残るかは未確認である
- **ekidata データの非加工での第三者提供は無償に限られる**（第6条）。
  公開API `/api/v1/*` が駅マスタを素に近い形で返すため、
  将来 furatora に有償プランを設ける際にこの条項の評価が要る
- **路線名・駅名が ekidata の表記へ置き換わるのは初回投入の一度きりである。**
  `常磐線快速` → `JR常磐線(上野～取手)` のような変化が公開サイトに現れる。
  以後の表記は Admin での手動編集で確定する
- **移行機構を削除するため、未突合行の解決手段は Admin の未突合解決UIに一本化される。**
  初回投入後に残る未突合は路線3件・駅4件である（2026-09-04 リハーサル実測）。
  いずれも現行DBの運行系統粒度と ekidata の線路名粒度が一致しないことによるものであり、
  突合の失敗ではない

## レビュー

以下のいずれかが起きたとき、本決定を再評価する。

- ekidata の提供停止・規約変更・更新頻度の劣化が起きた場合
- 駅ナンバリングが全国規模で要件になった場合。
  ekidata は会員版でも供給しないため、補完ソースの併用かハイブリッドの再検討になる
- 経路探索の実装方式が確定し、マスタの粒度に追加要求が生じた場合
- **手動維持の工数が見合わないと判明した場合。** 決定1の「継続同期を行わない」は
  年間の変更件数が少ないことを前提にしている。対応範囲の拡大などにより
  マスタの変更が恒常的に発生するようになれば、再取込の仕組みを再評価する
- ODPT の動的データを実際に利用する段になり、
  保持していた ID による突合が実用に耐えないと判明した場合
