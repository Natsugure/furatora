# ADR-0011: 乗換ルートの設備を「直列の並び」ではなく「種類の集合」で持つ

- **ステータス**: Accepted
- **日付**: 2026-09-25
- **決定者**: @Natsugure
- **関連**: [ADR-0012](./0012-zero-facility-route-as-not-entered.md),
  [`docs/domain/station-master-model.md`](../domain/station-master-model.md)「乗換難易度」節,
  GitHub Issue #30 / #122 / #123

---

## コンテキストと課題

乗換難易度の新モデル（Issue #30 で設計、#122 でスキーマ投入）は、ルートが通る設備を
`transfer_route_facilities` に `seq` 順の**直列の並び**として持ち、`unique (routeId, seq)` で
並びが壊れないことを守っていた。

ところが、ペルソナ（ベビーカー・車いす）ごとの「必要な行為」の導出は、
**ルート上の設備すべてから、そのペルソナにとって最も重いものを選ぶ**関数であり、順序に依存しない。
#30 の要件のうち順序を使うのは次の2点だけで、どちらも集合で足りる。

- 設備の並びを保持する
- 設備の並びと4フラグ（屋外・改札外・係員・公式案内）の一致で、重複ルートを検出する

一方で、順序を持つことのコストは具体的に発生していた。
Issue #123 は旧 `station_connections` の評価済み行を新モデルへ移すが、旧データの備考から言えるのは
「エレベーターを含む」といった**種類**までで、区間の順序は復元できない。
直列の並びのままでは、移行で確定できない情報を要求することになる。

判断時点で `seq` を読み書きするコードは存在せず、表は全環境で0行、
`seq` を作った 0009 は production に未適用だった。変更するなら今が最も安い。

## 決定

`transfer_route_facilities` から `seq` と `unique (routeId, seq)` を落とし、
`unique (routeId, typeCode)` を足す。1行は「このルートは、この種類の設備を**すべて通る**」を意味する。

- 順序も回数も持たない。同種の設備が何か所あっても1行になる。
- 同じ段差に対する代替手段（階段と階段昇降機など）は、同一ルートに入れず別ルートにする。
  集合は「すべて通る」を意味するため、同居させると判定が壊れる。
- 変更は新しいマイグレーション（`0011_transfer_route_facilities_as_set.sql`）で行い、
  適用済みの 0009 は書き換えない。

## 却下した選択肢

### 直列の並びを維持する

#30・#122 の設計のまま進める案。順序を使う導出が存在しないのに、入力（Admin の並べ替え UI）・
移行（旧データから復元できない順序の確定）・重複検出（並びの一致判定）のすべてに順序の確定を要求する。
得るものが「順序の表示」だけで、それを使う要件が現時点で無い。

### `seq` を nullable にして任意入力にする

順序が分かるルートだけ `seq` を入れる案。順序がある行と無い行が混在し、重複検出の一致判定が
「順序を見るか見ないか」の分岐を持つ。`unique (routeId, seq)` も NULL を素通しするため、
並びの不変条件を DB で守れなくなる。

## 影響

- 入力が「どの設備を通るか」だけになり、#124 の Admin に並べ替え UI が要らない。
- 重複ルートの検出が、設備の種類の集合と4フラグの一致判定になる。
- #123 の移行で、旧備考から言える範囲の設備を確定して投入できる。
- **失うもの**: ①「エレベーターで上がってから階段で降りる」といった順序の表示、
  ② 同種の設備の回数（「階段が2か所」）。必要な行為の6分類は回数を使わないため、現時点で影響は無い。
- 回数が必要になったら `count` 列を足す（追加なので非破壊）。順序が必要になった場合は、本ADRを覆す決定になる。

## レビュー

Web 表示（#125）で、設備の順序や回数の表示が必要になったとき再評価する。
回数だけなら `count` 列の追加で足り、本ADRは覆らない。
