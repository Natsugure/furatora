# ADR-0028: 依存の監査は high 以上で CI を落とし、moderate 以下は Dependabot のセキュリティ更新で片付ける

- **ステータス**: Proposed
- **日付**: 2026-11-07
- **決定者**: @Natsugure
- **関連**: [ADR-0026](./0026-pnpm-dependency-version-gates.md)（版を選ぶときの関所。Dependabot の `cooldown` をそろえる）,
  [ADR-0027](./0027-pnpm-catalog-for-shared-dependencies.md)（catalog で版を1か所に置く）,
  [ADR-0020](./0020-main-only-long-lived-branch.md)（main へのマージがそのまま本番に出る）

---

## コンテキストと課題

ADR-0026・ADR-0027 のもとで依存をまとめて上げ、`pnpm audit` の件数を減らした。
減らした状態を保つには、新しい脆弱性を見つけて止める仕組みが要る。

### 実測（2026-11-07）

| 確認項目 | 結果 |
|---|---|
| 対策前の `pnpm audit` | 204 件（low 17 / moderate 89 / high 85 / critical 13） |
| 依存の更新後の `pnpm audit` | 2 件（どちらも moderate・開発用の依存の配下） |
| 残る 2 件 | esbuild 0.18.20（GHSA-67mh-4wv8-2f99。drizzle-kit → `@esbuild-kit/*`。最新の drizzle-kit でも残る）、minimatch 10.2.6（GHSA-g3hv-75wg-m249。eslint-config-next の配下。修正は 11 系） |
| 監査の仕組み | CI に監査は無く、Dependabot も未設定だった |

### 課題

- 脆弱性は、依存を変えていなくても日々公開される。PR のときだけ監査しても、main に入った後に公開されたものは見つからない
- 監査で CI を落とす閾値を低くすると、上の 2 件のように直す手段が無いものでも CI が落ち続け、例外を書くしかなくなる
- `pnpm audit` の重大度は一般的な深刻さであり、このプロジェクトでの危なさではない

### 制約

- 開発者は1人。例外の管理に割ける手間は少ない
- main へのマージはそのまま本番に出る（ADR-0020）。CI を通らない PR はマージしない運用である

## 検討した選択肢

### 閾値

1. **監査を CI に入れない**（Dependabot のセキュリティ更新だけに任せる）
2. **moderate 以上で CI を落とす**
3. **high 以上で CI を落とし、moderate 以下は Dependabot のセキュリティ更新で片付ける** ← 採用
4. **critical だけで CI を落とす**

### 監査の範囲

A. **`--prod` を付け、本番の依存だけを監査する**  
B. **開発用の依存も含めて監査する** ← 採用

### PR で監査を回す条件（必須のチェックにしたうえで）

ア. **ワークフローを `paths` で絞る**  
イ. **すべての PR で監査を回す**  
ウ. **ワークフローはすべての PR で走らせ、依存を変えていなければ監査のジョブを `if:` でスキップする** ← 採用

## 決定

### 1. `pnpm audit --audit-level=high` で CI を落とす

- `.github/workflows/dependencies-audit.yml` で、次のときに回す
  - 依存を変える PR（`pnpm-lock.yaml`・`pnpm-workspace.yaml`・`package.json` を変えたとき）
  - 毎日の定期実行（main の上で、新しく公開された脆弱性を拾う）
- ジョブ `pnpm audit` を、main のルールセットの必須のチェックにする。
  CI を通らない PR はマージしない運用を、設定で強制する
- 依存を変えない PR では、監査のジョブをスキップして必須のチェックを通す。
  新しい high が公開されても、依存に関係ない急ぎの修正はマージできるようにするため
  - ワークフローは `paths` で絞らない。ワークフローが走らないと必須のチェックの報告が無く、待ちのまま残るため
  - 依存を変えたかは前段のジョブで判定し、監査のジョブを `if:` でスキップする。スキップは必須のチェックを満たす
- 監査は lockfile だけを読む。`pnpm install` はせず、監査の前に依存の install スクリプトを走らせない

### 2. moderate・low は CI を落とさず、Dependabot のセキュリティ更新で片付ける

- リポジトリの設定で Dependabot security updates を有効にする（`dependabot.yml` の版の更新とは別の設定）
- 本番の依存（`next`・`next-auth` など）の moderate は、セキュリティ更新の PR が来たら早めにマージする

### 3. `--prod` は付けない

開発用の依存も、install スクリプトや CI・手元での実行を通じて、供給網の攻撃の入り口になる。

### 4. high 以上の例外は、GHSA の ID で載せ、理由と期限を残す

- 直せない high 以上は、`pnpm-workspace.yaml` の `auditConfig.ignoreGhsas` に GHSA の ID で載せる
- 理由・解消の条件・見直しの期限を、載せた行のコメントで書く（ADR-0026 の決定3の例外と同じ形）。
  例外を外すときに説明も一緒に消えるよう、別のドキュメントには書かない
- 期限に達したら、直せるようになったかを確かめ、直せるなら直して例外を外す

## 各選択肢の評価

### 1. 監査を CI に入れない

- **良い点**: CI が依存の事情で落ちない。設定が要らない
- **悪い点**:
  - Dependabot は修正版がある脆弱性にしか PR を作らない。修正版が無いものは、通知を見に行かない限り気づかない
  - PR で high 以上を新しく引き込んでも、マージを止めるものが無い
- **却下理由**: main へのマージがそのまま本番に出るため、マージの前に止める仕組みが要る

### 2. moderate 以上で CI を落とす

- **良い点**: 見逃す脆弱性が減る
- **悪い点**:
  - 2026-11-07 の時点で、直す手段の無い moderate が 2 件ある。CI を通すには最初から例外を書くことになる
  - moderate は件数が多い（対策前で 89 件）。例外が増えると、1件ずつ理由を確かめずに載せるようになり、例外の管理が形だけになる
- **却下理由**: 例外が形だけになると、high 以上の例外まで確かめずに載せるようになる。moderate は修正版が出れば Dependabot が PR を作るため、CI で止めなくても片付く

### 4. critical だけで CI を落とす

- **良い点**: CI が落ちる場面がさらに減る
- **悪い点**: high には、リモートからの実行や認証の回避など、本番で直接悪用されうるものが含まれる（対策前は 85 件）
- **却下理由**: high を止めないと、本番で使う依存（`next`・`next-auth`）の深刻な脆弱性がマージを通る

### A. `--prod` を付け、本番の依存だけを監査する

- **良い点**: 開発用の依存の事情で CI が落ちない。今残る 2 件はどちらも開発用で、監査に出なくなる
- **悪い点**: 開発用の依存は、install スクリプトや CI・手元での実行の中で動く。侵害されると、手元の秘密情報や CI のトークンが漏れうる
- **却下理由**: 供給網の攻撃は、本番か開発用かを問わず入り口になる

### ア. ワークフローを `paths` で絞る

- **良い点**: 依存を変えない PR では、ワークフロー自体が走らない
- **悪い点**: ワークフローが走らないと、必須のチェックの報告が無く「Expected — Waiting」のまま残る。依存を変えない PR がマージできなくなる
- **却下理由**: 必須のチェックと両立しない

### イ. すべての PR で監査を回す

- **良い点**: 仕組みが単純。監査は 11 秒ほどで終わる
- **悪い点**: 新しい high が公開されると、直すか例外に載せるまで、依存に関係ない PR まですべて止まる
- **却下理由**: main へのマージがそのまま本番に出るため（ADR-0020）、セキュリティ以外の急ぎの修正を出せなくなるのは困る。
  依存を変えない PR は、新しい脆弱性を引き込まない

## 結果

### 肯定的な結果

- 依存を変える PR で、high 以上の脆弱性を新しく引き込むとマージできなくなる（必須のチェックで止まる）
- 依存を変えない PR は、監査の結果に関わらずマージできる。急ぎの修正が監査で止まらない
- 定期実行で、main に入った後に公開された high 以上の脆弱性に、翌日までに気づける
- 例外は GHSA の ID で載せるため、同じパッケージの別の脆弱性まで一緒に見逃すことは無い

### 否定的な結果・受け入れるトレードオフ

- moderate 以下は、Dependabot の PR が来るまで残る。修正版が無いものは残り続ける
- 定期実行で high 以上が見つかると、直すか例外に載せるまで、依存を変える PR がすべて落ちる
- 依存を変えない PR では監査が回らない。その間に公開された脆弱性は、定期実行が拾うまで分からない
- 修正版が公開から3日たっていないと、セキュリティ更新の PR も pnpm の `minimumReleaseAge` で install が止まる（ADR-0026）。
  急ぐときは、ADR-0026 の決定3に従って `minimumReleaseAgeExclude` に載せる

### 見直し条件

- 例外（`auditConfig.ignoreGhsas`）が増え続け、期限までに外せないものが目立つようになったとき。
  コメントでは見渡せなくなったら、例外の一覧を `docs/` 配下の専用のディレクトリに移すかを決める
- moderate の Dependabot の PR が溜まり、片付かなくなったとき
- pnpm 12 系へ移行するとき（#232）。`auditConfig.ignoreGhsas` は pnpm 11.15 以降で `audit.ignore` に改名されており、旧名は次のメジャー版まで読まれる
