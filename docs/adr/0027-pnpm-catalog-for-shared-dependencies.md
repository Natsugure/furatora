# ADR-0027: 2つ以上のパッケージで使う依存の版を、pnpm の catalog の1か所に置く

- **ステータス**: Proposed
- **日付**: 2026-11-07
- **決定者**: @Natsugure
- **関連**: [ADR-0026](./0026-pnpm-dependency-version-gates.md)（版は `^` を付けずに固定する）,
  [ADR-0015](./0015-shared-domain-packages-and-vocabulary.md)（アプリ間で共有する packages）

---

## コンテキストと課題

依存の版を、各パッケージの `package.json` がそれぞれ持っていた。
脆弱性対策で依存をまとめて上げる前に、版がどこに何か所書かれているかを数えた。

### 実測（2026-11-07）

| 確認項目 | 結果 |
|---|---|
| 2つ以上のパッケージ（ルートを含む）で使う依存 | 23 種類 |
| 書かれている場所が多いもの | `eslint` 7、`typescript` 7、`eslint-config-next` 6、`drizzle-orm` 4、`vitest` 4、`@types/react` 4 |
| 版の指定が食い違っていたもの | `next`（web `16.1.6` / admin `16.1.3`）、`typescript`（`^5` / `^5.7.2`）、`tsx`（`^4.21.0` / `^4.19.2`） |
| 版をそろえる必要があるのに食い違っていたもの | `@mantine/notifications` 8.3.15 が、`@mantine/core`・`@mantine/hooks` 8.3.15 を peer に求めるのに、8.3.14 が入っている |

### 課題

- 同じ依存の版を上げるのに、最大7か所を同じ値に書き換える必要がある。1か所の書き忘れが、そのまま食い違いとして残る
- `next` の食い違いは、web と admin で別の版のフレームワークが本番に出ていることを意味する。
  脆弱性の修正が片方のアプリにだけ入る状態が起こりうる
- `next` と `eslint-config-next`、`@mantine/*` のように、**組で同じ版にそろえる必要がある依存**がある。
  別々のファイルに書かれていると、組であることが読み取れない

### 制約

- pnpm 10.34.9（ADR-0026）。catalog は pnpm 9.5 から使える
- Dependabot が版を上げる PR を出す（ADR-0026 の決定4）。Dependabot は pnpm の catalog を書き換えられる
- 内部パッケージはどれも外部に公開しない（`private: true`）

---

## 検討した選択肢

1. **これまでどおり、各 `package.json` に版を書く**
2. **2つ以上のパッケージで使う依存だけを catalog に置く** ← 採用
3. **すべての依存を catalog に置く**
4. **ルートの `overrides` で版を強制する**
5. **各 `package.json` に版を書いたまま、食い違いを検査する道具（syncpack など）を CI に足す**

---

## 決定

### 1. 2つ以上のパッケージで使う依存を、`pnpm-workspace.yaml` の `catalog` に置く

- 「パッケージ」にはルートの `package.json` を含める
- 各 `package.json` では `"catalog:"` と書く
- catalog の版は `^` を付けずに固定する（ADR-0026）

### 2. 組で同じ版にそろえる依存は、1か所でしか使わなくても catalog に置く

- 例: `@mantine/notifications` は admin だけで使うが、`@mantine/core`・`@mantine/hooks` と同じ版を peer に求める
- `@next/third-parties`（web だけで使う）と `eslint-config-next` は、`next` と同じ版にそろえる。
  catalog では隣に並べ、コメントで組であることを示す

### 3. catalog に置かないもの

- 1つのパッケージでしか使わず、組にも属さない依存。その `package.json` に固定した版で書く
- `peerDependencies`。範囲（`^19` など）のまま、各パッケージに書く。利用する側の版を縛らないため
- `workspace:*` の内部パッケージ

### 4. パッケージごとに版を意図して変えるときは、名前付きの catalog を使う

段階的な移行（片方のアプリだけ先にメジャー版を上げる）などで、版を意図して分けるときは、
`catalogs:` に名前付きの catalog（例: `next17`）を作り、そのパッケージだけ `"catalog:next17"` と書く。
理由と、既定の catalog へ戻す条件をコメントで書く。
各 `package.json` に版を直接書いて分けることはしない。分けていることが catalog を見ても分からなくなるため。

## 各選択肢の評価

### 1. これまでどおり、各 `package.json` に版を書く

- **良い点**: 新しい仕組みが要らない。各パッケージが自分の依存を自分で読める
- **悪い点**: 実測のとおり、すでに3種類で食い違いが起きている。1回の更新で書き換える場所が多く、書き忘れが残る
- **却下理由**: 食い違いを防ぐ手段が、人の注意しか無い

### 3. すべての依存を catalog に置く

- **良い点**: 版を探す場所が常に1か所になる
- **悪い点**: 1か所でしか使わない依存まで、使う場所と版を書く場所が離れる。
  そのパッケージを読むだけでは版が分からなくなる
- **却下理由**: 食い違いが起こりえない依存に、離れる不便だけを持ち込む

### 4. ルートの `overrides` で版を強制する

- **良い点**: 直接依存だけでなく、配下の依存の版もそろえられる
- **悪い点**: `overrides` は依存の解決を上書きする仕組みで、配下の依存にも効く。
  各 `package.json` に書いた版と、実際に入る版が食い違って見える
- **却下理由**: 直接依存の版をそろえる目的には効きすぎる。
  `overrides` は、親を上げても消えない配下の依存の脆弱性に限って使う

### 5. 食い違いを検査する道具を CI に足す

- **良い点**: 各 `package.json` に版を書いたまま、食い違いを見つけられる
- **悪い点**: 書き換える場所の数は減らない。依存（道具）が1つ増える
- **却下理由**: pnpm に組み込みの catalog で、食い違いがそもそも起こらない形にできる

---

## 結果

### 肯定的な結果

- 共有する依存の版を上げるとき、書き換えるのは `pnpm-workspace.yaml` の1行になる。Dependabot の PR も1行の差分になる
- web と admin が、同じ版のフレームワークで本番に出る
- 組でそろえる依存が、catalog の中で隣に並ぶ

### 否定的な結果・受け入れるトレードオフ

- catalog にある依存は、各 `package.json` を読んでも版が分からない（`pnpm-workspace.yaml` を見る必要がある）
- 2つ目のパッケージで使い始めた依存を、catalog へ移す作業を人が忘れうる。`pnpm add` は自動で catalog へ移さない
- 1つのパッケージでしか使わない依存は、引き続き各 `package.json` で版を管理する

### 見直し条件

- 2つ目のパッケージで使い始めた依存が catalog へ移されずに残ることが続いたとき。
  `catalogMode`（`pnpm add` で catalog の使い方を強制する設定）の導入を検討する
- pnpm 12 系へ移行するとき（ADR-0026 の見直し条件）。catalog の書き方が変わっていないかを確かめる
