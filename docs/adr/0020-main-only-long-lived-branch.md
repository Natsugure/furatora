# ADR-0020: 長命ブランチを main のみにし、PR はマージコミットで main へ入れる

- **ステータス**: Accepted
- **日付**: 2026-10-20
- **決定者**: @Natsugure
- **関連**: [ADR-0008](./0008-environment-database-branch-mapping.md)（「制約」のブランチ運用と、`preview/develop` をステージングとする記述を置き換える）,
  GitHub Issue #183

---

## コンテキストと課題

これまでのブランチ運用は git-flow（`feature/*` → `develop` → `main`）だった。開発者は1人である。

### 実測（2026-10-20）

| 確認項目 | 結果 |
|---|---|
| `origin/main` と `origin/develop` の差 | 内容は同一。main がマージコミット10個分だけ先行し、develop にしか無いコミットは0 |
| main の直近のマージ | 「Merge pull request … from Natsugure/develop」のリリース PR が交互に並ぶ |
| ruleset「Protect main branch」 | `enforcement: active` だが、対象（`conditions.ref_name.include`）が空。`rules/branches/main` は空で、**main に効いているルールが無い** |
| 同 ruleset の除外者 | リポジトリ管理者（`RepositoryRole` 5）が `bypass_mode: always` |
| リポジトリのマージ方法 | マージコミット・Squash・Rebase のすべてを許可。マージ後のブランチ削除は無効 |

### 課題

- `develop` は、内容が同じ2本のブランチを同期させるためのリリース PR とマージコミットを生み、コンフリクトの原因になっている
- `develop` が担う役割は、ADR-0008 の「`preview/develop` が実質のステージング環境」だけである。
  一方で PR ごとの Preview は、Neon の `preview/<git-branch>`（`main` のデータのコピーにその PR のスキーマを当てたもの）につながり、
  ステージングより本番に近い状態で確かめられる
- main は Production であり、マージするとビルド時にマイグレーションが走る（ADR-0008）。
  それにもかかわらず、main を守るルールが実際には効いていない

### 制約

- 開発者は1人。レビュアーは Claude（PR のレビュー）
- CI（`.github/workflows/ci.yml`）は `pull_request` で起動する
- Neon の preview ブランチの削除は PR のクローズで起動する（`.github/workflows/cleanup-neon-preview.yml`）
- 複数の PR にまたがる作業（例: #166 のデザイン刷新）は gh-stack で PR を積み、すべてそろうまで公開できないことがある

---

## 検討した選択肢

### ブランチ構成

1. **git-flow を続ける**（`develop` を残す）
2. **長命ブランチを main のみにし、作業ブランチから PR で main へ入れる（GitHub Flow）** ← 採用
3. **main へ直接 push する（PR を使わないトランクベース）**

### マージ方法

A. **Squash に統一する**
B. **マージコミットに統一する** ← 採用
C. **Rebase に統一する**

---

## 決定

### 1. 長命ブランチは `main` だけにする

- 作業ブランチは `main` から切る。名前はこれまでどおり `feat/` `fix/` `refactor/` `chore/` `docs/` + `issueN-…`
- 作業ブランチは PR で `main` へマージする。PR の Preview（Vercel と Neon の `preview/<git-branch>`）と CI がステージングの役割を担う
- `develop` ブランチと、Neon の `preview/develop` ブランチは消す

### 2. 公開を待つ複数 PR の作業は、まとめ役のブランチを一時的に作る

すべてそろうまで公開できない作業は、`main` から一時的なまとめ役のブランチ（例: `feat/issue166`）を切る。
子の PR はそこへ積み（gh-stack）、最後にまとめ役のブランチを PR で `main` へ1回だけマージして消す。
独立して公開できる PR は、まとめ役のブランチを使わず直接 `main` へ入れる。

### 3. マージはマージコミットに統一する

- リポジトリの設定で、マージコミットだけを許可する。マージ後の作業ブランチは自動で消す
- 作業ブランチの中では、意味のある単位でコミットする（その分け方を main に残す）
- PR 全体を戻すときは `git revert -m 1 <マージコミット>` を使う。
  戻した PR を出し直すときは、先に revert の revert をしてから修正を積む
  （同じコミットを再マージしても、Git は取り込み済みとみなして変更を入れないため）

### 4. main を ruleset で実際に守る

- ruleset「Protect main branch」の対象を既定ブランチ（`~DEFAULT_BRANCH`）にする
- ルール: 削除の禁止・強制 push の禁止・PR を必須・CI（`verify`）の成功を必須
- 管理者の除外は `bypass_mode: pull_request` にする。直接 push は管理者でも拒否し、
  緊急時は PR のマージに限って CI を待たずに入れられる

### 5. 破壊的マイグレーションの二段階（ADR-0008）は、2つの PR を順に main へ入れる形になる

1 の PR をマージして本番に出たことを確かめてから、2 の PR をマージする。

## 各選択肢の評価

### 1. git-flow を続ける

- **良い点**: `preview/develop` で、複数の PR を合わせた状態を本番の前に確かめられる
- **悪い点**:
  - 同じ内容の2本を保つためのリリース PR とマージコミットが、PR のたびに要る
  - `preview/develop` は作られた時点から main のデータとずれていく（ADR-0008「否定的な結果」）。
    PR ごとの Preview のほうが本番に近い
  - 複数の PR を合わせて確かめたい作業は、決定2のまとめ役のブランチで同じことができる
- **却下理由**: 1人の開発では、得られる検証がまとめ役のブランチで代替でき、同期の手間とコンフリクトだけが残る

### 3. main へ直接 push する

- **良い点**: PR を作る手間が無く、最も単純
- **悪い点**:
  - CI は `pull_request` で起動するため、検証を通らずに本番へ出る
  - Neon の preview ブランチの削除が PR のクローズに結びついている
  - main への push は、ビルド時のマイグレーションを含めて即座に本番へ出る
- **却下理由**: main が本番そのものであり、PR を通すことが唯一の検証点になる

### A. Squash に統一する

- **良い点**: main が 1 PR = 1 コミットになり、PR 全体を `git revert <sha>` の1回で戻せる
- **悪い点**:
  - 作業ブランチの中で分けたコミット（「ADR を Accepted にする」「レビューの指摘を直す」など）が main から消え、
    PR の一部だけを戻すことも、`git bisect` で PR の中まで絞ることもできない
  - gh-stack で積んだ PR では、下の PR を Squash でマージすると、上の PR のブランチが元のコミットを持ったままになり、
    作り直し（rebase）とコンフリクトの原因になる。`develop` をやめる目的と逆行する
- **却下理由**: このリポジトリはコミットを意味のある単位に分けており、PR を積む運用もある

### C. Rebase に統一する

- **良い点**: 履歴が一直線になり、コミットの分け方も残る
- **悪い点**: PR の境目が履歴に残らない。PR 全体を戻すには、そのコミットを1つずつ revert する必要がある
- **却下理由**: PR 単位で戻せることを、履歴の見た目より優先する

## 結果

### 肯定的な結果

- リリース PR と、`develop` の同期によるコンフリクトが無くなる
- 確かめる環境が PR ごとの Preview に一本化され、本番のデータに近い状態で確かめられる
- main への直接 push と、CI を通らない PR のマージが、ルールで止まるようになる

### 否定的な結果・受け入れるトレードオフ

- PR をマージすると、そのまま本番に出る（マイグレーションを含む）。本番の前に、複数の PR を合わせた状態を確かめる場所は、
  まとめ役のブランチを作ったときにしか無い
- main の履歴にマージコミットが残り、一直線にはならない
- 管理者は PR のマージに限ってルールを迂回できる。緊急時の逃げ道として残す

### 見直し条件

- 開発者が複数人になり、PR のレビューの承認を必須にする必要が出たとき
- 本番の前に、複数の PR を常に合わせて確かめる必要が出たとき（ステージングの常設を再検討する）
- Vercel や Neon の Preview の仕組みが変わり、PR ごとの Preview が本番のデータのコピーにつながらなくなったとき
