# ホームの座標系

ホーム上の位置は、すべて**メートル単位の1次元連続座標**で表現する。
設備・車両停車位置・乗り換え帯は、同一のホームについては同一の座標系に乗る。

## 原点

**`x = 0` はホームの物理的な一端**であり、ホームの実体は区間 `[0, physicalLength]` である。

**原点は列車のデータから導出しない。** どの停車位置パターンが登録・削除されても
原点は動かない。これが本座標系の中心的な性質であり、以下がその帰結である。

- 停車位置パターン同士は互いに独立している。あるパターンの追加・削除が
  他のパターンや設備の座標に影響しない
- 設備の座標は、列車のデータが1件も無い状態でも確定できる

### どちらの端を `x = 0` にするか

**線路に向かって立ったときの左の端を `x = 0` とする**（[ADR-0022](../adr/0022-platform-origin-left-end-facing-track.md)）。
`x` は右の端へ向かって増える。号車番号の向き（1号車がどちらの端か）とは無関係である。

これにより、図は「線路に向かって立った見え方」でそのまま描ける。
**図は回してよいが、鏡写しにしてはならない。** 号車番号は列車の側の事情で、
同じホームに号車が逆の列車が来る（埼京線と湘南新宿ライン）ため、
1号車の位置を基準に図の向きを決めることはしない。

- Web・Admin とも **x昇順で左→右**に描画し、列車を上（奥）、ホーム上のものを下（手前）に置く
- 新しいホームを入れるときも、外部の資料（駅の構内図など）の向きにかかわらず、この約束で座標を入れる。
  Admin のホームの編集欄（ホームの物理長の説明）にこの約束を示している
- **ホーム端に方面ラベルを出さない**。方面（`inbound` / `outbound`）はホームの左右端に紐付いていない

将来「← 渋谷方面」を端に表示する場合は、`platforms` に「`x=0` 側がどの方面か」を
持つカラムを1つ追加すればよい。**原点が動かないため、既存座標は一切壊れない。**

## ホームの物理長

`platforms.physicalLength`（`decimal(6, 2)`、メートル）。管理者が Admin で手入力する
のが唯一の供給経路である（外部データソースからは取得できない）。
既存行のために `default('0')` を付けて追加しており、**`'0'` は「未入力」を意味する。**
`NOT NULL` の default を外す作業は後続Issue。

## 座標の範囲

`[0, physicalLength]` の**外側にも配置できる**。負の座標も許容する。

頭端式ホームの外側にある改札、ホーム端より先に伸びる通路など、
「ホームの物理的な範囲の外だが、ホーム座標系で位置を語れるもの」を表現するため。
バリデーションで範囲を制限しない。

## 単位と精度

| 対象 | 型 | 備考 |
|---|---|---|
| `platforms.physicalLength` | `decimal(6, 2)` | |
| `trainStopPatternCars.startMeters` / `endMeters` | `decimal(6, 2)` | |
| `trainCarStructures.carLength` | `decimal(5, 2)` | nullable |
| `platformLocationCells.xPositionMeters` | `decimal(6, 2)` | nullable（null = コンコース全体） |
| `facilityConnections.xRangeStart` / `xRangeEnd` | `decimal(6, 2)` | nullable（対面乗り換え帯） |

`decimal` を使うのは浮動小数点誤差による表示崩れを避けるため。
Drizzle は `decimal` を **`string` で返す**ので、`number` への変換は
`external/query/` の中で行い、DTOより上の層に `string` を渡さない。

## 描画

SVG の `viewBox` を用い、ホーム物理長・設備位置・車両停車位置をすべて
同一のメートル座標系で描画する。

### 横方向

描画範囲は `physicalLength` と全設備・全停車位置パターンの座標から
マージンを加えて動的に算出する（`features/platform/domain/geometry.ts` の `computeBounds()`）。
範囲外の設備も描画対象に含める。

**アクセス点の描画範囲は、座標そのものではなく設備アイコンの張り出しを含む。**
1つのアクセス点に設備が複数あると、アイコンは中心の左右へ扇状に並ぶ
（`FACILITY_ICON_PITCH` = 7m 間隔、1辺 `FACILITY_ICON_SIZE` = 6m）ため、
片側の張り出しは1件で3m・2件で6.5m・3件で10mになる。`computeBounds()` と
`DiagramSvg` は同じ定数（`facilityIconHalfExtent()`）を使い、
「描いたのに viewBox の外で切れた」が起きないようにしている。

メートル → 画面ピクセルの換算率は **5px/m 固定**（`features/platform/domain/geometry.ts` の
`PX_PER_METER`）。図全体を載せる**キャンバス**の最小幅が「描画範囲 × 5px」となり、
コンテナに収まらない分は横スクロールで見る。画面幅に応じて縮小はしない
（viewBox単位で指定した文字が判読できなくなるため）。

キャンバスに与えるのは `width` ではなく **`min-width`** である。コンテナのほうが広ければ
キャンバスは伸びて余白を埋める。伸縮しても各層の位置は割合で決まるのでずれない（後述）。

**この横スクロールは、キャンバスを包む祖先の flex アイテムに `min-width: 0`
（Tailwind の `min-w-0`）が当たっていることに依存する。** flex アイテム既定の
`min-width: auto` のままだと、幅がキャンバスの `min-width` まで膨らんでスクロールが
成立せず、カードの `overflow-hidden` に無言で切り落とされる。

### 縦方向

**縦方向は実寸ではない。** 横方向と単位（メートル）は共通だが、値は
「列車行 / 隙間 / 設備行 / 束ね線」を積んだ図式的な高さである。

列車行を上に置き、**ホーム上にあるものはすべて列車行の下**（線路に向かって立った人の側）
に配置する。ホーム帯・乗車位置目標・設備行・コンコース束ね線がこれに当たる。
対面乗り換えのティントは、ホーム側の帯全体（列車の下端から設備行の下端まで）を覆う。
縦の座標は `geometry.ts` の `layoutRows()` が返す。ホームの側による分岐は無い。

SVGの高さは `layoutRows().viewHeight` で決まり、**22（束ね線ありで 24）で固定**である。
出口・乗り換えのラベルはSVGの外にあるので、コンコースが何件あっても伸びない。

### レイヤ構成 — SVG と HTML オーバーレイ

図は**3つの層**でできており（Admin はこの上にさらに編集レイヤを重ねる。後述）、
すべてが1つのキャンバス（`min-width` = 描画範囲 × `PX_PER_METER`）
の上に、上から 対面乗り換えバナー → 図 → 出口・乗り換えプレート の順で積まれる。

| 層 | 実体 | 内容 |
|---|---|---|
| 対面乗り換えバナー | HTML | 「◯◯線（△△方面）は同じホームの向かい側に到着」 |
| 図 | SVG | ホーム帯・乗車位置目標・号車・設備アイコン・束ね線・対面乗り換えティント |
| 出口・乗り換えプレート | HTML | 出口名（バター色）と乗り換え先（白＋黒枠） |

**層をまたぐ x の対応は、ピクセルではなく割合で取る。**
`geometry.ts` の `xFraction(x, bounds)` が 0..1 を返し、SVG は viewBox のメートル座標で、
HTML は CSS のパーセントで同じ割合に落ちる。キャンバスが伸縮しても対応は崩れない。

> **`<svg>` に明示的な `height`（Tailwind の `h-*` を含む）を指定してはならない。**
> 指定すると要素ボックスのアスペクト比が viewBox とずれ、`preserveAspectRatio="xMidYMid meet"`
> がレターボックスを作る。SVG の中身だけが縮んで x 写像が壊れ、オーバーレイとの対応が
> 無言でずれる。高さは viewBox と幅から決まるものとして、指定しないこと。

プレートの段（レーン）は、CSSでは**単一セルの grid** として組む。同じセルに置かれた
grid item は全員が行の高さに寄与するので、レーンの高さが中身に合わせて自動で決まる。
絶対配置は使わない（高さに寄与せず、行の高さをサーバ側で推定する羽目になり、
推定を外すと段が重なって読めなくなる）。

**レーン0は常に図に接する側に置く。** 図の下にあるプレートは段を正順に、
図の上にある対面乗り換えバナーは段を逆順に描く。

### 編集レイヤ（Admin、絶対配置の4層目）

Admin の駅レイアウトページ（`/stations/[stationId]/layout`）は、上記3層の上に
**ドラッグ可能なハンドル**を絶対配置で重ねる（`packages/platform-diagram` の
`PlatformDiagram` が公開する `diagramOverlay` render prop、
`apps/admin/src/features/station-layout/components/DiagramEditLayer.tsx`）。
SVGの再レイアウトは行わない。

**x と y で位置の取り方が非対称である**点が上記3層と異なる:

- **x はここでも割合で取る**（`xFraction(x, bounds) * 100%`）。上記の規約と同じ。
- **y は実測ピクセルで取る**。`<svg>` は `height` を指定しない前提（上記）だが、
  `preserveAspectRatio="xMidYMid meet"` は要素ボックスが viewBox より**高い**とき
  `min(rw/vw, rh/vh) = rw/vw`（幅律速）になり、x は正しいまま y だけ
  `(要素の高さ - viewHeight × scale) / 2` だけずれる。アスペクト比が一致していれば
  このオフセットは0になるが、「一致している」こと自体は実測でしか確認できない
  ため、y はハンドル配置のたびに `getBoundingClientRect()` から計算する。

**bounds の凍結**: `computeBounds()` は全座標から算出するため、ドラッグ中に
座標が動くと bounds も動き、図全体がスケールし直してドラッグが暴れる。
Admin 側は、保存が確定した値（baseline）が変わったとき（マウント時・保存成功時）
だけ bounds を再計算する（`StationLayoutEditor` の該当コメント参照）。
ドラッグ中の未保存値（draft）は bounds の算出に含めない。

**座標編集の入力経路は2つあるが、状態は1つ**: アクセス点・号車境界の座標は
図上ドラッグ（本節）と、インスペクタの数値入力
（`components/inspector/ConcourseInspector.tsx`/`StopPatternInspector.tsx`）の
どちらからも編集できる。両方とも `apps/admin/src/features/station-layout/domain/
editDraft.ts` の同じ純関数（`moveCell`/`moveCarBoundary`/`moveCarEdge`）を呼ぶため、
どちらの経路で編集しても未保存state・不変条件（号車境界の隙間・重なり防止、
向き非依存の判定）は1箇所に閉じたまま保たれる。数値入力専用の別ロジックを
作らないこと。

### コンコースの表現

コンコース（`platformLocations`）は座標を持たない。**その位置は、属するアクセス点
（`platformLocationCells.xPositionMeters`）の範囲として表す。**

同一コンコースのアクセス点は**束ね線（ブラケット）**で結び、その先に
出口名（`exits`）と乗り換え先（`facilityConnections`）の**プレート**を置く。
これが「同一コンコース単位のグルーピング」の図的表現であり、
「どの階段・エレベーターがどの出口・どの乗り換えに通じるか」を図だけで読めるようにする。

プレートは駅サインの様式（地の色と枠で種類を分けた札）に従う。
**出口はバター色の地に濃い文字と濃い輪郭、乗り換えは白地に黒枠**（色は [ADR-0018](../adr/0018-semantic-colors-for-facilities.md)）。
出口の地は白地からほとんど浮かないため、プレートの外形は輪郭が受け持つ。
乗り換え先は路線ごとに路線カラーのチップを添えて縦に並べる。

- **図のプレートは全文を表示する。省略しない。** 乗り換え先の路線名は
  「接続先駅に乗り入れる全路線」なので大規模駅では長くなるが、
  プレートはHTMLなので折り返して収まる（[ADR-0006](../adr/0006-diagram-text-in-html-overlay.md)）
- 座標を持つアクセス点が1つも無いコンコースは束ね線を引けないため図に描けない。
  出口名・乗り換え先ともに、SVG外のテキストリストに委ねる
- プレートどうしが横方向に重なる場合は段（レーン）を分けて積む。
  **どの段に置くかは `domain/concourseLayout.ts` の `layoutConcoursePlates()` が決め、
  段の高さはCSSが決める。** 文字幅の推定は段の割り当ての判断にのみ使い、
  切り詰めには使わない。推定を外してもプレートが折り返すだけで情報は失われない
- **引き出し線は、手前のレーンのプレートの脇を折れ線で迂回する。**
  深いレーンのプレートへ降りる線が、手前のレーンのプレートと横位置で重なるときは、
  隣り合うプレートの隙間（同一レーンの間隔 `PLATE_GAP_PX` の中央）へ逃がす
  （`domain/leaderRoute.ts` の `routeLeaders()`）。横移動は各レーンの図に近い側の
  余白帯の中だけで行い、プレートの文字を覆わない。描画範囲の端に寄せられた
  プレートの上を通る線は、範囲内に残る側へ自動的に回る
- 迂回の経路は幅の**見積り**から導くため外れうる。両側とも逃げ場が無い場合は線を動かさず
  （`passesBehindPlate`）、重なり順（縦線0 < プレート1 < 余白帯の横線2）を `z-index` で
  明示することで、線はプレートの背面を通る。**線がプレートの文字を覆うことはない**
- 束ね線とプレートの対応は、幾何だけに頼らず**文章でも担保する**。
  出口プレートの見出しに、そこへ通じる設備の種別名を添える

**図とテキストリストは役割が違う。図は位置関係の把握、リストは図に描けないものの受け皿である。**
テキストリストが受け持つのは、座標を持たないコンコース（束ね線を引けないもの）である。

### 駅ページでの出し方（番線のカード）

> **適用状況**: 図は今のところ、どの幅でも横の図だけ。`lg` 未満の縦の図は #174 の後続の PR で加わる（ADR-0023）。

ホーム図は番線ごとの別ページを持たず、駅ページの**番線のカード**（`apps/web/src/features/platform/components/`）に収める（ADR-0023）。

| 画面の幅 | カード |
|---|---|
| `lg`（1024px）未満 | 折りたたみ。既定で閉じる。開いている間は、頭と下の端の両方に閉じる操作がある。下の端で閉じると、頭のボタンへフォーカスを戻す |
| `lg` 以上 | いつも開いている。開け閉めの操作は無い |

- **カードの頭には、番線・路線・編成・方面だけを出す。** 編成は、番線に停まる列車の両数を重複を除いて小さい順に並べる
  （「8・10両編成」。`features/platform/domain/formation.ts`）。列車が無ければ出さない
- **図を描けない番線**（ホーム長が `0`、または列車が無い）は、閉じた状態の頭に「図はまだありません」と出す。
  開いているとき（`lg` 以上ではいつも）は中身が理由（ホーム長が未登録／列車情報が無い）を示すので、頭には出さない。
  そのうえで位置未登録のコンコースも注記も無ければ、開いても頭と同じことしか出ないので、開け閉めの操作を出さない
- **見た目の開閉の切り替えは CSS（`lg:`）だけで行う。** 最初の描画（サーバー）から PC で開いた形になる。
  `lg` 以上で頭をボタンにしないこと（支援技術に、見えている中身を「折りたたまれている」と伝えないため）だけは、
  マウント後に `useMediaQuery` で切り替える（`PlatformCard.tsx`）
- **図の下に、フリースペースと優先席のドアの一覧を出す**（読み上げ・テキスト検索のため。優先席は図に描かないので、ここにだけ出る）。
  それぞれ「全編成」「一部編成」の見出しで分け、空の見出しは出さない。同じドアに全編成と一部編成の両方があれば、
  図と同じく全編成だけに出す（`domain/consist.ts` の `standardByDoor()`、`domain/doorList.ts` の `doorListGroups()`）

## 号車の向き

**向きを表すカラムは持たない。** 列車の向きは号車座標そのものが表現する
（1号車が x の小さい側にあるか、大きい側にあるか）。

ドア番号の反転表示は、`cars` を `carNumber` 昇順に並べたときの
`startMeters` が減少していれば反転、として導出する（`domain/doorOrder.ts`）。

個々のドアの座標は `domain/consist.ts` の `doorCenterX()` が返す。
号車をドア数で等分した**スロットの中心**であり、左端ではない。
乗車位置目標はこの中心に打つ。

## この文書を変更するとき

**原点の定義（`x = 0` の位置）を変更する場合、保存済みの全座標の再計算が必要になる。**
`trainStopPatternCars` / `platformLocationCells` / `facilityConnections` の
すべてのメートル値が対象で、機械的な一括変換で済むとは限らない。
変更には明示的な意思決定を要する。
